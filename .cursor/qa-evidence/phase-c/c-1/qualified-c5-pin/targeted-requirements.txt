## REQ-BDC-0720: The sync on the cache's cron table

**Status:** Approved (Rand, 2026-10-26)

beads-cache syncs bd on rows of the sc-cron table inside the cache file (ADR-BDC-0014): at most one built-in sync row per repository (a Rust job) and at most one Python sync row running a consumer's script; at most one of them is enabled at any time. `bdc cache schedule set <cron-expr> [--budget-ms N] [--hook-reserve-ms N] [--post-sync <module:function> --python <interpreter> [--env NAME]...]`, `schedule show`, `schedule enable`, `schedule disable` and `schedule clear` manage the built-in row; `enable` and `disable` flip only its `enabled` flag, and `schedule enable` while the Python row is enabled is `SCHEDULE_INVALID` (`details.reason: "python_sync_enabled"`). `schedule set` writes the row in one store transaction (sc-cron's `replace_and_set_enabled`, REQ-CRON-0017): an existing row keeps its `enabled` flag, a new row is enabled unless the Python row is enabled (then it is written disabled), and a row written enabled disables the Python row in the same transaction, so no connection ever sees both rows enabled. `--budget-ms` defaults to 25000 (1000–600000); `--hook-reserve-ms` defaults to 5000 (0 to budget − 1000, and at least 1000 when a hook is named). The built-in row's sc-cron timeout is `budget_ms + 10000`, so sc-cron never aborts a run before its hook and its lease release. The built-in row's run takes the lease, drains, syncs every configured scope and calls the post-sync hook; `bdc cache cron run`, `cron run --once`, `bdc cache tick` and PyO3 `Cache.tick()` run that same Rust code. While the Python row is enabled, `bdc cache tick` and `Cache.tick()` are refused with `PRECONDITION` (`details.reason: "python_sync_enabled"`) and start no bd process. Scheduled times come only from the rows; an on-demand tick does not change them.

**Source:** S83, S90, A3, A4, A7; Rand, 2026-10-26

## REQ-BDC-0721: Scopes are configured bd filters

**Status:** Approved (Rand, 2026-10-26)

A scope is a validated name plus a bd filter: `All`, or criteria over labels (all of, any of), status, type and assignee (ADR-BDC-0013). `.beads/bd-cache.toml` defines scopes with `[[scope]]` tables and the `scopes` string list; a scope it defines is created or updated in the store's registry on open, and `scopes set` or `scopes remove` of it is `CONFIG_INVALID`. Other scopes are managed with `bdc cache scopes add|set|remove|list` (and PyO3 `scopes_*`). The built-in row syncs every configured scope. Removing a scope deletes its membership rows, not bead rows another scope still holds. A run with no scopes still drains and runs the hook.

**Source:** A5, A7; ADR-BDC-0013

## REQ-BDC-0722: One sync at a time

**Status:** Approved (Rand, 2026-10-26)

Every sync run, built-in or Python, scheduled, on demand or the immediate run of `sync use-python`, takes the one `tick_lease` row of the cache file under `BEGIN IMMEDIATE` before it starts, expiring at its deadline plus 10 s, and releases it on every exit path. A run that finds a live lease does nothing: a scheduled or on-demand run replies `skipped: "in_flight"` (exit 0), and `sync use-python` fails with `TICK_IN_FLIGHT` (retryable). `sync use-builtin` takes no lease, so it works whenever a built-in row exists; a Python run already in flight keeps the lease until it ends or its worker cancels it on seeing the change (REQ-CRON-0014), and the built-in row's next run is skipped as `in_flight` until it ends. An expired lease, such as one left by a holder killed with `kill -9`, is taken over; lease expiry is the only cover for a holder that is killed outright.

**Source:** S90, A7; ADR-SYNC-0008

## REQ-BDC-0723: The post-sync hook runs isolated

**Status:** Approved (Rand, 2026-10-26)

bd-cache-sync runs the post-sync hook named in the built-in row's payload as `<absolute interpreter> -I -m bd_cache_rs.run post_sync <module:function>` through sc-cron's exported child-process supervisor (REQ-CRON-0018): from a private temp cwd, with the environment cleared except `PATH`, `HOME`, the locale variables, `BEADS_DIR`, `BD_CACHE_PATH` (the cache file) and the row's `--env` names, stdout and stderr each capped at 1 MiB and stderr kept in the reply truncated to 8 KiB, killed with everything it started at its deadline (NFR-BDC-0004). There is no in-process call. No row's or hook's code runs from a cache file that is not owned by the current user, or that is group- or world-writable (Unix; the Windows ACL check is a documented gap): the check runs before every launch, for the hook and for the Python sync row alike.

**Source:** S89, S90, A7; ADR-SYNC-0008

## REQ-BDC-0724: Switching to a consumer's Python sync

**Status:** Approved (Rand, 2026-10-26)

`bdc cache sync use-python --python <absolute interpreter> --module <module> [--cron <expr>] [--timeout-ms N] [--env NAME]...` checks its inputs, takes the lease, then in one store transaction (sc-cron's `replace_and_set_enabled`, REQ-CRON-0017) writes the one Python sync row enabled, created or replaced in place, and disables the built-in row if there is one, then runs the row at once under that lease with the events of a scheduled run, so the caller sees any error the script emits. A re-run with a new script, module, expression, timeout or `--env` list replaces the one Python row in place (its generation raised, so a run of the old one is fenced); there is never a second Python sync row. The reply carries the run id, the exit status and the script's stderr (truncated to 8 KiB, with the values of the row's `--env` variables redacted). A failed run (non-zero exit, timeout, spawn failure, oversize output, a stop answer other than `continue`, an untrusted cache file, or a signal to the command) makes the command fail with `TICK_RUN_FAILED` after restoring, in one transaction, the state held before the command: the Python row's previous contents and flag (or, if there was none, the new row disabled) and the built-in row's previous flag. So a failure from mode `builtin` returns to `builtin`, a failed re-run from mode `python` returns to `python` with the previous script, and a failure when there is no built-in row leaves both rows disabled (mode `none`). If that restore fails the error says so (`details.restored: false`) and names `bdc cache sync use-builtin` as the recovery. `bdc cache sync use-builtin` makes the built-in row the enabled one in one transaction and always works when a built-in row exists; with none it is `SCHEDULE_INVALID` (`details.reason: "no_builtin_row"`) naming `bdc cache schedule set`. Neither command, nor `schedule set`, leaves both rows enabled at any moment. A relative or missing interpreter, one that is not a regular executable file, one that cannot `import bd_cache_rs` within 5 s, a module that is not a dotted name, or a timeout outside 1000–600000 ms (default 60000) is `SCHEDULE_INVALID`. `--cron` defaults to the built-in row's expression and is required when there is none. `.beads/bd-cache.toml` cannot name code to run (`CONFIG_INVALID`).

**Source:** S89, A7; Rand, 2026-10-26 (ruling 9); ADR-SYNC-0008

## REQ-BDC-0725: A consumer's Python sync replaces the built-in one

**Status:** Approved (Rand, 2026-10-26)

With the Python sync row enabled, the consumer's script is the only sync: no `bd list` runs for the configured scopes, and the script fills the cache through `ingest_scope`. The script is run with sc-cron's Python hook protocol: `cron.stop` before every run (answered `{"action": "continue"}` to go on), then `cron.tick`, each with one JSON object on stdin whose `payload` carries `cache_path`, `beads_dir` and the run's `run_id`; its environment is the allowlist of REQ-BDC-0723. `bd_cache_rs.sync.main(func)` is the harness a script calls: it answers `cron.stop` with `continue` and, on `cron.tick`, opens `Cache` on the payload's cache file and calls `func(cache, payload)`. The row's run is judged by its exit status, as any sc-cron row, and its timeout is the row's `--timeout-ms`.

**Source:** S87, A7; Rand, 2026-10-26 (ruling 9); ADR-SYNC-0008

**Status:** Approved (Rand, 2026-10-26)

`ingest_scope(scope, rows, blocked, revision=None, allow_empty=False)` (Rust, `bdc cache scopes ingest` with JSON on stdin, PyO3) applies the strict row decoder, declared membership, the built-in `blocked` rule, the newer-row guard and one transaction; an empty snapshot is refused unless allowed; at most 50 000 rows and 64 MiB per call, enforced while the input is read (stdin is read through a 64 MiB + 1 byte limit and rows are counted as they decode, so an oversized input is refused before it is held whole); any violation is `INGEST_INVALID` with the stored scope untouched.

## REQ-BDC-0727: The post-sync hook gets every result, and delivery is at-least-once

**Status:** Approved (Rand, 2026-10-26)

After the built-in sync, the post-sync hook named in its row's payload gets the drain result, each scope's result and error with `failing_since` and `notified`, the escalated entries not yet notified (oldest first, at most 500, with `escalated_truncated` and `escalated_remaining`), and the pending count, in a request of at most 4 MiB, with at least `hook_reserve_ms` left. The run marks nothing; anything the hook does not mark is offered again on a later run, with `first_offered_at` unchanged; the hook must be idempotent. Consecutive hook failures are counted (`hook_state`). From the third, the hook is backed off: it is next called after a wait that starts at one period of the row and doubles with each further failure, capped at one hour, and the first success clears the count. One *period* of a row is the gap between its next two scheduled times at evaluation: its stored next run and the run after that, jitter included (QA97R2-016). It is the expression's interval for a regular expression; for an irregular one (`0 0,5 * * * *`) it follows the next run (5 minutes, then 55); a row with no next run, or none after it, has no period, and the wait is then the one-hour cap; the count, the last error and the next attempt show in `schedule show` and health. The cache sends nothing (ADR-BDC-0010).

**Source:** S88; ADR-SYNC-0008

## REQ-BDC-0729: Outage is classified, and the new codes are typed

**Status:** Approved (Rand, 2026-10-26)

Errors that can come from bd carry `details.outage: bool`, true only when bd could not be reached (spawn failure, timeout, lock, transport); a `BD_LIST_FAILED` from a bd that answered has `outage: false`. The new codes:

| Code | Kind | CLI exit | Retryable | Raised by | `details` keys | `suggested_action` |
|---|---|---|---|---|---|---|
| `INGEST_INVALID` | invalid_input | 3 | no | `ingest_scope`, `scopes ingest` | `scope`, `reason` (`row_invalid`, `empty`, `too_many_rows`, `too_large`, `membership`), `index` for a row | fix the named row or limit and resend the whole snapshot |
| `SCHEDULE_INVALID` | invalid_input | 3 | no | `schedule set|enable`, `sync use-python` | `field`, `reason` | fix the named option; switch rows with `bdc cache sync use-python|use-builtin` |
| `TICK_RUN_FAILED` | unavailable | 3 | no | `sync use-python`, `cron run --once`; also embedded, as an error object, in the `hook.error` member of a built-in run's reply, whose own exit is 0 (`ok: true`) | `row`, `run_id`, `reason` (`exit`, `timeout`, `spawn`, `oversize`, `stop_answer`, `untrusted`, `signal`), `exit_status`, `stderr`, `restored` (the command form only) | read `stderr`; `bdc cache sync use-builtin` restores the built-in sync |
| `TICK_IN_FLIGHT` | conflict | 3 | yes | the lease, for `sync use-python`; a scheduled or on-demand run that finds the lease replies `skipped: "in_flight"` with exit 0 instead of raising it | `holder` (`pid`, `host`, `expires_at`) | retry after `expires_at` |

Each code is one row of `ERROR_TABLE` and of the contract's §4 error table, with the exit above; where it is also embedded in a reply is said in its details, not by a second row. Sprint b-7 adds the four rows to both tables, and sprint b-8 removes the `TICK_<REFUSAL>` family with the refusals it reported (ADR-BDC-0015).

**Source:** ADR-BDC-0005, ADR-BDC-0015, A7

## REQ-BDC-0730: `cron run` stops cleanly

**Status:** Approved (Rand, 2026-10-26); amended at the phase-end review (PE1-RSH-007: a second signal ends the wait; confirmed by Rand, 2026-10-26)

`bdc cache cron run` handles `SIGINT` and `SIGTERM` (Ctrl-C and Ctrl-Break on Windows): it starts no new run, waits for the runs in flight up to `--shutdown-timeout-ms` (default 10000, 0–600000), then kills every run still going together with its process tree (the hook's and the Python row's), releases the lease on every exit path, and exits 130 for `SIGINT`, 143 for `SIGTERM`, and 130 for Ctrl-C or Ctrl-Break on Windows. `SIGHUP` is handled as `SIGTERM` (exit 129). A second signal during the wait ends it at once: the bd calls stop and every run still going is killed with its process tree, as when the timeout expires, and the exit code stays the first signal's (*amended at the phase-end review; it was ignored before*). A `kill -9` is covered only by lease expiry. `cron run --once` waits for each run it started up to that run's own deadline, then exits 0, or 3 with `TICK_RUN_FAILED` naming each failed row. `cron run` logs to stderr through a process-wide subscriber at the `-v`/`-q` levels, one structured event per run step (lease, drain, each scope, hook, reply) with the row, the run id and the outcome, and sc-cron's own events.

**Source:** Rand, 2026-10-26 (ruling 5); ADR-SYNC-0008

## REQ-BDC-1002: Published scheduler ownership and compatible SQLite

**Status:** Approved (phase C, explicit project-owner execution approval, 2026-11-02)

beads-cache must consume the published sc-runtime scheduler, or the exact
qualified prerelease Git candidate in ADR-BDC-0016, instead of maintaining
and publishing its local sc-cron prototype. All workspace rusqlite consumers must
use the 0.39 line matching sc-runtime. The existing BD-CACHE v3 identity, rows,
journal, scope/schedule state, sync replacement and shutdown guarantees must survive

## ADR-BDC-0005: The backend may be slow or unreachable

**Status:** Approved (lead ruling 2026-10-24: approved with the phase-a plan, merged by the owner in PR #1)

Context: two deployments are expected: a dolt server on a remote machine over
an unreliable network, and a local server on a host so loaded that `bd`
calls take seconds (the BD-CACHE motivation). BD-CACHE v3 escalates a write
after `MAX_ATTEMPTS` (5) transient failures, so a backend outage of a few
cron ticks escalates every pending write to the phase's recipient.

Decision:
- Reads never wait long on the backend. Every read reply carries the scope's
  `last_ok_at` and `stale` per row, so callers and MCP tools can see how
  fresh the data is. A cache miss fetches with a short deadline
  (`CacheConfig::miss_fill_timeout`, default 2 s) and returns
  `BD_CACHE.BD_UNAVAILABLE` when it expires.
- Backend unreachable (timeout, connection refused, cannot start) at the
  backend check, the drain pre-read or a sync or refresh list is a backend
  state, recorded in the store as the outage (since when, latest error). It
  is cleared only by a `bd list` that answers: `bd version` can pass while
  lists time out on a loaded host. A write that fails or times out counts an
  attempt, as in v3, since it may have reached the backend. While it holds, the drain
  stops without counting an attempt, and a sync that meets it records the
  outage instead of an announced `SYNC_FAILED`. These are the rules v3 adopted
  in the v3 baseline (Rand approved); the two implementations must apply the
  same rules because they share a journal, and only one may drain it.
  Only failures from a reachable backend (`BD_WRITE_FAILED`, guard refusal)
  count towards `MAX_ATTEMPTS` or escalate.
- No extra backoff: the cron tick (30 s) is the retry interval. `status`
  reports the outage. An outage is announced through each active scope's
  sync alert under the stable cause key `backend_unavailable`, so each recipient
  hears it once; its end resets the alert without a message.
- The drain has a start gate and a hard deadline (REQ-BDC-0402): each `bd`
  call is capped at the time left before the hard deadline; a call cut short
  by it is neither an outage nor an attempt.

Consequences: a long outage leaves writes pending rather than escalated; when
the backend returns, preconditions are re-checked against fresh rows, so
conflicting changes made elsewhere still escalate. Changes BD-CACHE's
retry-cap behaviour; needs agreement on #557.

## ADR-BDC-0013: Scopes are named bd filters

**Status:** Approved (Rand, 2026-10-26). Amends ADR-BDC-0001 (the scope kinds), ADR-BDC-0002
(how the ready and blocked base is fetched), ADR-BDC-0007 (`sc-beads`' `ScopeFilter`),
ADR-BDCLI-0001 (the scope argv), ADR-MODEL-0003 (its fix-a-1-1 amendment's `ScopeId::Phase(PhaseName)`
and its a-7 amendment's `PhaseName::RULE`), ADR-CORE-0204 (`ScopeId::from_labels`), ADR-STORE-0003's
a-7 amendment (S34: a `scopes` entry that is not a phase name) and REQ-STORE-0007 (the same
rule in the loader); referenced from ADR-STORE-0006. Sprint b-7 makes each of these changes.

Context: Rand ruled (2026-10-25, Amendment A5) that a scope is defined by a filter, not by the
first consumer's phase naming, and that `--all` is a scope. Today `ScopeId` is
`enum { Phase(PhaseName) }`, `sc-beads`' `ScopeFilter` is only `Label(String)`, `sc-bd-cli`
builds only `-l <label>` argv for `bd list`, `bd blocked` and `bd ready`, the `scope` table is
`(name, kind)`, and the fakes answer only a label.

Decision:
- **Types, validated once in `bd-cache-model`.** `ScopeName` keeps `PhaseName`'s rule: a
  non-empty string of ASCII letters, digits, `.`, `_` and `-`, with no length cap. That rule
  admitted every name a v3 file holds, so every stored scope stays valid and none is refused or
  renamed; no stricter rule is added, because a scope's name is never passed to bd (its filter's
  labels are). `ScopeName::RULE` replaces `PhaseName::RULE` as the one text of the rule.
  `ScopeFilter`: `All`, or `Criteria { labels_all, labels_any, status, issue_type, assignee }`,
  where `labels_*` are sets of labels, `status` a set of bd statuses, `issue_type` and
  `assignee` optional strings. A `Criteria` with every field empty and any request that sets
  `all` together with a criterion are refused at construction (`InvalidValue`; `BAD_ARGS` in
  `bd-cache-api`, `CONFIG_INVALID` in the configuration). `ScopeId` becomes the scope's name
  (`ScopeId(ScopeName)`, with `name()`); `ScopeId::Phase`, `PhaseName` as a scope kind and
  `ScopeId::label()` go. A `Scope` is `{ id: ScopeId, filter: Option<ScopeFilter> }`, where
  `None` is a phase-a scope (below). `bd-cache-api`, `bd-cache-cli` and `bd-cache-py` take these
  types and never re-validate.
- **Two filter types, one conversion.** `bd_cache_model::ScopeFilter` is the validated scope
  filter, `status` included; `sc_beads::ScopeFilter` is the backend's and has no `status`,
  because bd is never sent one. They are distinct types joined by one conversion,
  `bd_cache_model::ScopeFilter::backend(&self) -> sc_beads::ScopeFilter`, which drops `status`
  and turns a `Criteria` whose only criterion is `status` into `All`; `bd-cache-model` no longer
  uses the sc-beads type as its own. The two refusals above are made once, in the model's
  constructor; sc-beads takes its variants as given, and `sc-bd-cli` and `FakeBackend` refuse
  an empty sc-beads `Criteria` (`InvalidValue`, before any bd call), which the conversion never
  produces.
- **`sc-beads`.** `ScopeFilter` (already `#[non_exhaustive]`) gains `All` and
  `Criteria { labels_all, labels_any, issue_type, assignee }`; `Label(l)` stays and means
  `labels_all = [l]`. `CacheBackend`'s scope calls keep their signatures. `FakeBackend` answers
  every variant.
- **`sc-bd-cli` argv, per variant** (`<all seven>` is the existing status list):

  | Call | `All` | `Criteria` |
  |---|---|---|
  | list | `bd list --all --status <all seven> -n 0 [--updated-after c] --json` | `bd list [-l a,b] [--label-any c,d] [-t type] [-a who] --status <all seven> -n 0 [--updated-after c] --json` |
  | blocked | `bd blocked --json` | `bd blocked [-l a,b] [--label-any c,d] --json` |
  | ready | `bd ready -n 0 --json` | `bd ready [-l a,b] [--label-any c,d] [-t type] [-a who] -n 0 --json` |

  `status` is never passed to bd: the sync lists all seven statuses (REQ-BDC-0501) and the store
  applies the status criterion to membership, so a bead that leaves the status set leaves the
  scope on the next sync that lists it. `bd blocked` takes no type or assignee flags, so the
  blocked and ready answers are intersected with the scope's membership. A bead that stops
  matching a criterion bd applies (a label, type or assignee) keeps its membership until a sync
  lists it again, as a removed label does today. Verified: the flags above are those `bd list
  --help`, `bd blocked --help` and `bd ready --help` print for bd 1.3.0 on the development host
  (`bd list`: `-l` all, `--label-any` any, `-s`, `-t`, `-a`, `--all`, `-n`; `bd blocked`: `-l`,
  `--label-any`, `--exclude-label`, `--parent`; `bd ready`: `-l`, `--label-any`, `-t`, `-a`,
  `-n`); the repository's bd 1.3.1 fixtures record only `-l`. Sprint b-7 records bd 1.3.1
  fixtures for each variant, `FakeBd` and the `fake-bd` binary answer them, and the bd-compat
  workflow checks them against bd 1.3.1.
- **Base (amends ADR-BDC-0002 item 1).** A scope's ready and blocked base is the `bd blocked`
  and `bd ready` answer of the table above, intersected with the scope's members, stored with
  its fetch time; the local adjustment and the bounded fresh answer are unchanged.
- **Store.** Stored scope names stay as written: phase a stores the bare name (`scope(name, kind
  = 'phase')`, `sync_state.phase`, `scope_member.scope`, `journal.phase`), and nothing is
  renamed. A nullable `scope.filter` column holds the filter as JSON. NULL, on every
  `kind = 'phase'` row, keeps the phase-a meaning: a label scope whose label is
  `LEGACY_SCOPE_PREFIX` followed by the name (a stored `x` syncs the label `<prefix>x`). The JSON
  is written only for a scope created in phase B with a filter. The v3 `beads.phase` column
  keeps its phase-a meaning, the first legacy-prefixed label of the row, and is NULL for a row
  with no such label: a filter scope never writes its name there, so a row only a filter scope
  holds has `phase` NULL. The column is in ADR-STORE-0006's list and the format golden.
- **Source of truth.** `.beads/bd-cache.toml` defines scopes with `[[scope]]` tables (`name`
  plus the filter keys `labels_all`, `labels_any`, `status`, `type`, `assignee`, or `all =
  true`) and with the existing `scopes` string list (each string a phase-a scope, by the 0.1
  rule below). A scope the
  file defines is created or updated in the store's registry when the cache opens, and
  `scopes set` or `scopes remove` of it is `CONFIG_INVALID` (`details.source:
  "config_scope"`): the file wins. Any other scope lives in the registry only and is managed
  with `bdc cache scopes add|set|remove`. Syncing a name that is neither registers it on demand
  as a label scope with that one label (REQ-BDC-0909). Only a sync registers on demand (`cache
  refresh scopes <name>` and the 0.1 `sync(phase)`); every other verb that names a scope refuses
  an unknown name with `SCOPE_UNKNOWN` and registers nothing.
- **0.1 compatibility (Rand, 2026-10-26).** Where a 0.1 interface took a phase (the `scopes`
  string list and the 0.1 Python verbs), `x` and `<prefix>x` both mean the phase-a scope stored
  as `x`, whose label is `<prefix>x`: the 0.1 meaning, with the prefix the one constant
  `LEGACY_SCOPE_PREFIX` (ADR-BDC-0012). Every other interface (the `[[scope]]` tables, the CLI,
  the 0.2 Python namespaces and the new methods) takes a scope name as written: `x` names the
  scope stored as `x`, and `<prefix>x` names a scope stored under that longer name. The prefix
  rule is applied on the 0.1 paths only.
- **Callers.** The `ScopeId` change ripples into `bd-cache`, `bd-cache-store`, `bd-cache-api`,
  `bd-cache-cli` (with the `fake-bd` binary), `bd-cache-py` and `bd-cache-sync`; sprint b-7
  makes those edits mechanically, so the workspace builds green, and the semantic removals stay
  with b-8.
- **Register text this changes.** ADR-MODEL-0003's fix-a-1-1 amendment (scopes are
  `ScopeId::Phase(PhaseName)`) now reads `ScopeId(ScopeName)`, and `PhaseName::RULE` in its a-7
  amendment is `ScopeName::RULE`. ADR-CORE-0204's `ScopeId::from_labels` finds the first
  legacy-prefixed label through `LEGACY_SCOPE_PREFIX` and returns the phase-a scope it names; the
  rest of that ADR holds. ADR-STORE-0003's S34 amendment and REQ-STORE-0007: `store_config_bad_scope`
  is a `scopes` entry or a `[[scope]]` name that is not a valid `ScopeName`, or a `[[scope]]`
  filter refused above, and its fix states `ScopeName::RULE`; a valid name in the `scopes` list
  is a phase-a scope, never a `ConfigLoadError`.

Consequences: REQ-BDC-0501, 0602, 0603, 0901, 0909 and 0721 are amended; the contract's scope
text (§5, §6, §12) is rewritten by b-9 from this ADR. Tests `sync_label_filter_scope` and
`sync_all_scope` pin the two new variants end to end against the fakes.

## ADR-BDC-0014: The schedule rows live in the cache file through sc-cron's store trait

**Status:** Approved (Rand, 2026-10-26). Amends ADR-BDC-0006 (the schedule store), ADR-STORE-0003
(one connection per process), ADR-STORE-0006 (the schedule table), ADR-CRON-0006 (the store a
caller supplies), NFR-BDC-0007 and REQ-CRON-0009.

Context: the sync rows must live in the cache file (S83, ADR-BDC-0011), but sc-cron's
`SqliteScheduleStore` owns its own file and connection, refuses a file that holds other tables
("sc-cron needs its own database file") and owns `PRAGMA user_version` (its `SCHEMA_VERSION`
is 2), while the cache file is frozen at `user_version` 3 and a process holds one connection to
it (NFR-BDC-0007, ADR-STORE-0003). sc-cron's `Scheduler::new` already takes any
`Arc<S: ScheduleStore>`, so a caller can supply the store.

Decision (Rand's ruling, 2026-10-26):
- `sc_cron::ScheduleStore` is the seam. `SqliteScheduleStore` (its own file, `user_version` 2)
  stays sc-cron's standalone default, unchanged.
- `bd-cache-store` implements `sc_cron::ScheduleStore` as `CacheScheduleStore`, over the cache's
  single SQLite connection: `SqliteStore`'s connection moves behind a mutex shared by the store
  handle and `SqliteStore::schedule_store()`, so the process opens no second connection. The
  shared, mutex-guarded object owns both the connection and the per-process claim (`Registration`,
  `STORE_IN_USE`), the claim after the connection so the connection closes first, as today: the
  claim is released only when the last holder of the connection drops. A `CacheScheduleStore`
  that sc-cron's `Scheduler` holds after the `SqliteStore` handle is dropped therefore keeps the
  claim, and a second `SqliteStore` open in the process is still `STORE_IN_USE`. The schedule
  table, `sc_cron_schedule`, with sc-cron's version-2 columns and checks, is an additive table in the cache file, created
  through the extension mechanism (ADR-STORE-0006).
- The cache file stays `PRAGMA user_version` 3. The version of sc-cron's columns in the cache
  file is the `meta` row `sc_cron_schedule_version` (2), written and checked by
  `CacheScheduleStore`, never `user_version`; a cache file whose row names another version is
  refused with `StoreErrorKind::SchemaMismatch` before any schedule is served.
- A general store change sc-cron needs (several rows' enabled flags in one transaction, and a
  row written with its flag together with other rows' flags, REQ-CRON-0017) is a required
  `ScheduleStore` method that both implementations provide in one `BEGIN IMMEDIATE`.
- `bd-cache-store` gains the workspace edge `bd-cache-store` → `sc-cron`; `sc-cron` still depends
  on no bd-cache crate.

Consequences: `schedule set` and `cron run` open the schedule store at startup and fail with a
typed error (`STORE_FAILED` with `details.source` naming the check) before serving any work.
Sprint b-7 implements the trait change and `CacheScheduleStore`, with an acceptance test that a
v3 cache file with scopes gains the schedule table and stays `user_version` 3, that the process
holds one connection to the cache file, and that the claim outlives a dropped `SqliteStore`
while the schedule store is alive.

## ADR-BDC-0015: The new verbs are modelled in bd-cache-api and run by the front ends

**Status:** Approved (Rand, 2026-10-26). Amends ADR-BDC-0009 (where the new verbs execute),
ADR-CLI-0003 (the command table), ADR-CLI-0004 (the legacy-directory refusal is removed) and
ADR-PY-0005 (through ADR-PY-0006).

Context: phase B adds `bdc cache scopes add|set|remove|list|ingest|announce`, `cache schedule
set|show|enable|disable|clear`, `cache cron run [--once]`, `cache sync use-python|use-builtin`
and their Python methods, with the codes `INGEST_INVALID`, `SCHEDULE_INVALID`,
`TICK_RUN_FAILED` and `TICK_IN_FLIGHT`. ADR-BDC-0009, ADR-CLI-0003, REQ-BDC-0807 and
REQ-CLI-0006 require one `bd-cache-api` decoder and one set of models for the CLI, Python and
MCP; `bd-cache-api` must not depend on `bd-cache-sync` or `sc-cron`. The new `scopes list`
would collide with `cache scopes`, and `scopes remove` with `cache evict`.

Decision:
- **Models in `bd-cache-api`.** Every new verb's request, its reply data and its errors are
  `bd-cache-api` types (pure data: no `bd-cache-sync`, no `sc-cron`), decoded by the one decoder
  (`src/decode.rs`) and listed in `Command::ALL`; `cache tick` becomes a `Command` too, so the
  `request/mod.rs` doctest that `Command::parse("cache tick")` is `None` is reversed, and
  `src/ops/mod.rs` declares the new ops module and its `execute` arms.
  The store-only verbs (`scopes add|set|remove|list|ingest|announce`) also execute in
  `bd-cache-api` over `bd-cache`, like the other management verbs.
- **Execution in the front ends.** `schedule *`, `cron run`, `tick` and `sync use-python|use-builtin`
  need `bd-cache-sync`, so `bd-cache-api` decodes them into a request the front end executes:
  `bd-cache-cli` (`src/request.rs` and its `commands/`) and `bd-cache-py` (ADR-PY-0006) call
  `bd-cache-sync`. The MCP server, later, does the same.
- **Codes.** The four new codes are rows of `ERROR_TABLE`, with the kinds and exits of the code
  table in REQ-BDC-0729. The `TICK_<REFUSAL>` family (`ApiError::tick_refusal` and its kind
  table) is removed with the refusals it reported (b-8).
- **Verb names.** `cache scopes` stays the read verb and is `scopes list`'s alias: both return
  the same reply, now with each scope's filter. `cache evict <scope>` stays and empties a
  scope's beads as today; `scopes remove <scope>` is `evict` followed by removing the scope from
  the registry, refused (`PRUNE_BLOCKED`) under the same rule as `evict`. Neither old verb
  changes its arguments or reply members; new members are additive.
- **Configuration (amends ADR-CLI-0004).** The refusal of the legacy cache file in the first
  consumer's own directory is removed: the cache file is found by the store's rules or named by
  `cache_path`, and no consumer path is known to beads-cache.

Consequences: sprint b-8 owns the `bd-cache-api` request, data and error files for these verbs
and `bd-cache-cli/src/request.rs`; b-9 writes the contract text from this register. REQ-BDC-0810,
REQ-CLI-0006 and REQ-CLI-0008 are amended.

## REQ-API-0001: One decoder, nothing ignored

**Status:** Approved (lead ruling S60, bc-lead, 2026-10-25; phase B closed, 2026-10-25); amended by ADR-BDC-0015

`decode(command, json)` is the only path from a JSON request to a typed
request. An unknown member is `BAD_ARGS` with `details.member`; a `/v0`
parameter or member of the pinned spec (beads v1.3.2) that the cache does not
serve is `UNSUPPORTED` with `details.unsupported` and `details.name`; unknown
members are reported before unsupported ones. An empty patch and
`status: "closed"` are `BAD_ARGS`; a patch is validated as the journal parses
it (`Op::parse_new`).

Decode, then `execute`, is the only path: `Request` and its per-command
structs have crate-private fields (read through accessors), the unit
requests are `#[non_exhaustive]`, and the per-command operations are
crate-private, so no front end can build or alter a request the decoder did
not check (QA RCR-001). Operation-level `UNSUPPORTED` is left to the front
end, which builds it with `ApiError::unsupported(Unsupported::Operation, name)`.

*Amended by ADR-BDC-0015 (Rand, 2026-10-26): the phase-B verbs' requests, reply data and errors are this crate's types, decoded by the one decoder; this crate still depends on neither `bd-cache-sync` nor `sc-cron`, and the front ends execute the verbs that need them.*

**Refines:** REQ-BDC-0807
**Acceptance evidence:** `decode_refusals` (`tests/fixtures.rs`, fixture `decode_refusals.json`); the `compile_fail` doctests in `src/lib.rs` (a literal `IssuesUpdate`, a field changed after decoding, `ops::issues_update`); `an_operation_the_cache_does_not_serve_is_unsupported_operation` (`tests/error_table.rs`).

## ADR-STORE-0001: The file schema: v3 unchanged plus additive extensions

**Status:** Approved (lead ruling, bc-lead, 2026-10-24); amended by ADR-STORE-0004 (a-7: `ready_base_blocked`, `ready_base.indexed`, `journal.applied_epoch`, `journal_applied_epoch`, `journal_applied_unknown`; the index `journal_applied_at` of an earlier a-7 build is dropped; amended by sprint b-1 (contract §9, lead ruling S62: `journal.last_error_code`, `journal.note`, `journal.changed`; see "Amendment b-1" below); amended by ADR-STORE-0006 (the phase-B extensions; the in-repo evidence of the b-1 amendment becomes the format golden)

Context: the file is shared with the baseline Python implementation (REQ-BDC-0804) at
`user_version` 3 (REQ-BDC-0103). Phase a needs scopes with membership
(ADR-BDC-0001), a per-scope ready base (ADR-BDC-0002), `applied_at` for the
ready adjustment, and room for an HTTP backend (ADR-BDC-0004). P-2 (agreement
with the first consumer) is open; its fallback is additive tables and
nullable columns only, with no version change.

Decision: the v3 tables and indexes are created with the baseline Python implementation's DDL
text, unchanged (`meta`, `beads`, `edges`, `journal`, `sync_state`;
`beads_phase`, `edges_target`, `journal_pending`). The extensions, created on
open when absent, are:

```sql
CREATE TABLE scope (name TEXT PRIMARY KEY, kind TEXT NOT NULL DEFAULT 'phase');
CREATE TABLE scope_member (scope TEXT NOT NULL, bead TEXT NOT NULL, PRIMARY KEY (scope, bead));
CREATE INDEX scope_member_bead ON scope_member(bead);
CREATE TABLE ready_base (scope TEXT PRIMARY KEY, blocked_json TEXT NOT NULL,
  ready_json TEXT NOT NULL, fetched_at TEXT NOT NULL, stale INTEGER NOT NULL DEFAULT 0);
CREATE TABLE ready_base_blocked (scope TEXT NOT NULL, bead TEXT NOT NULL,
  blocked_by_json TEXT NOT NULL, PRIMARY KEY (scope, bead)) WITHOUT ROWID;   -- ADR-STORE-0004
ALTER TABLE ready_base ADD COLUMN indexed INTEGER;       -- ADR-STORE-0004
ALTER TABLE beads ADD COLUMN membership_known INTEGER;   -- ADR-STORE-0002
ALTER TABLE beads ADD COLUMN revision TEXT;              -- ADR-BDC-0004
ALTER TABLE journal ADD COLUMN applied_at TEXT;          -- set by apply_with_readback
ALTER TABLE journal ADD COLUMN applied_epoch INTEGER;    -- ADR-STORE-0004: Unix seconds of applied_at
ALTER TABLE journal ADD COLUMN last_error_code TEXT;     -- b-1: the CODE of last_error
ALTER TABLE journal ADD COLUMN note TEXT;                -- b-1: the resolve note
ALTER TABLE journal ADD COLUMN changed INTEGER;          -- b-1 (S62): 1 / 0, stored with the entry
ALTER TABLE sync_state ADD COLUMN backend_kind TEXT;     -- ADR-BDC-0004
ALTER TABLE sync_state ADD COLUMN endpoint TEXT;
ALTER TABLE sync_state ADD COLUMN replica_id TEXT;
ALTER TABLE sync_state ADD COLUMN journal_seq INTEGER;
CREATE INDEX beads_membership_unknown ON beads(id) WHERE membership_known IS NULL;
DROP INDEX IF EXISTS journal_applied_at;                 -- ADR-STORE-0004: an earlier build's expression index
CREATE INDEX journal_applied_epoch ON journal(applied_epoch) WHERE state = 'applied';          -- ADR-STORE-0004
CREATE INDEX journal_applied_unknown ON journal(seq) WHERE state = 'applied' AND applied_epoch IS NULL;  -- ADR-STORE-0004
```

No index holds a function (ADR-STORE-0002, ADR-STORE-0004). Open also runs the `applied_epoch`
backfill of ADR-STORE-0004.

Scopes are keyed by phase name (`ScopeId::name`), as the v3 `phase` columns
are. `row_json` is the normalized row (REQ-BDC-0108) with its outgoing edges
as `{issue_id, depends_on_id, type}`, rendered as Python's
`json.dumps(sort_keys=True)`; the `phase` column is the first valid
`phase-<x>` label. On read, `dependencies` comes from `edges` (the authority;
the baseline Python implementation keeps bd's full dependency objects in `row_json`), and the rest
of `row_json` is decoded with the row model's serde shape (unknown keys
refused, ids validated), the exact inverse of the encoding. The ready base's
lists are JSON arrays of `BlockedRow` and bead ids. The outage and sync
alerts are the v3 `meta` keys (`outage_since`, `outage_error`,
`sync_alert:<phase>`); clearing the outage also clears
`outage_announced_at`, as the baseline Python implementation does. `user_version` stays 3: 0 is
initialized, 3 opened, any other value refused and left unchanged.

Consequences: the baseline Python implementation opens the extended file (its `CREATE ... IF NOT
EXISTS` and column-named inserts ignore the additions) and its `status`
shows the extra `sync_state` columns. A later version change is an explicit
migration command, never done on open.

## ADR-STORE-0002: Sharing the file with the baseline Python implementation

**Status:** Approved (lead ruling, bc-lead, 2026-10-24); revised by fix-a-4-2 (lead ruling, bc-lead, 2026-10-24); Concurrency bullet amended by ADR-STORE-0004 (lead rulings S25/S26, bc-lead, 2026-10-24) and by the bounded marker writes (lead ruling S33, bc-lead, 2026-10-24); amended by ADR-STORE-0006 (cross-implementation evidence moves to the consumer's own test against the published wheel; the in-repo evidence is the format golden)

Context: the baseline Python implementation writes the same file and knows nothing of the
extensions. Its `INSERT OR REPLACE INTO beads(...)` resets the extension
columns of the rows it stores; its `prune` deletes beads by the `phase`
column; its rebuild deletes `beads`, `edges` and `sync_state`. Either may run
while the other has the file open.

Decision:
- **Membership.** `beads.membership_known` is 1 on every row this store
  writes. A row with `membership_known IS NULL` was last written by
  the baseline Python implementation; its membership is its v3 `phase` column, which is how
  the baseline Python implementation itself lists a phase. Reads apply that rule directly
  (`rows_in_scope`, `status`), so a row the baseline Python implementation writes while this store
  is open reads correctly at once. Open and `prune_scope` take such rows
  over (membership from `phase`, `membership_known = 1`) and drop
  `scope_member` rows whose bead no longer exists; an upsert takes over the
  row it stores. A bead deleted by the baseline Python implementation and stored again unscoped is
  a new row with no membership, so stale memberships never revive.
- **Ready bases** that the baseline Python implementation's rebuild or prune leaves behind are
  kept; the next sync of the scope replaces them (a-6), and their rows are
  read as absent until then.
- **Drain lock.** The lock file is named as v3 names it (the cache file's
  extension replaced by `drain.lock`), so the two drains exclude each other.
- **`synced_at`.** The v3 column is `NOT NULL` but neither implementation
  reads it; `upsert_rows` takes no time, so the store writes SQLite's
  current UTC time, as the baseline Python implementation writes its own clock. No value the port
  returns depends on it; every other timestamp comes from the caller.
- **Concurrency.** Every mutating method is one `BEGIN IMMEDIATE`
  transaction under the 5 s busy timeout, as the baseline Python implementation's writes are,
  single-statement ones included (`SqliteStore::write`). **Exception**
  (ADR-STORE-0004, lead rulings S25/S26): the journal reads `has_entries_since`
  and `applied_since` may run one autocommit `UPDATE` that dates entries
  the baseline Python implementation applied while the store is open, only when more than
  `READ_DATING_THRESHOLD` (2000) such entries wait, and with the busy timeout
  set to zero, so they never wait for the write lock; the answer is the same
  whether or not the `UPDATE` runs. **Bounded marker writes** (lead ruling S33,
  below). Every read that
  needs more than one value sees one snapshot: `status`, `get_row` and
  `rows_in_scope` run in one read transaction (`SqliteStore::read`);
  `outage` (both meta keys) and `open_work` (both counts) are one statement
  each. Open checks `user_version` and `project_id` (and creates the
  schema) before it sets WAL, so a refused file keeps its journal mode;
  the baseline Python implementation's own order (WAL first) does not constrain ours.
- **Bounded marker writes (S33).**
  **Status:** Approved (lead ruling S33, bc-lead, 2026-10-24).
  `mark_announced_within` and `set_sync_alert_within` (port methods whose
  provided bodies ignore the wait, for a store that never waits) run their one
  `BEGIN IMMEDIATE` transaction with the busy timeout `min(BUSY_TIMEOUT, wait)`
  and put `BUSY_TIMEOUT` back after it (`SqliteStore::write_within`; `BusyWait`,
  the drop guard the read-path dating uses at zero, also restores on unwind).
  The tick passes the time it has left, so a write lock another process holds
  cannot carry it past its end; a lock held past the wait is the usual
  `STORE_FAILED` (`database is locked`) and nothing is written. The store keeps
  the SQLite details: the caller passes a `Duration`, never a pragma.
  `mark_announced` and `set_sync_alert` are these with `BUSY_TIMEOUT`. Tests:
  `a_bounded_marker_write_waits_at_most_its_wait_and_restores_the_timeout`
  (unit; the timeout sampled inside each write by a temporary trigger: the wait,
  zero, and `BUSY_TIMEOUT` for a longer wait) and
  `a_bounded_marker_write_gives_up_on_a_held_lock_within_its_wait`
  (`tests/store.rs`; a lock held by another connection until both writes have
  returned).
- **Database names.** `DoltDatabase` is stricter than the baseline Python implementation (which
  refuses only `/`): the name becomes a file name on every supported
  platform, so `\`, `: * ? " < > |`, control characters, a trailing dot or
  space and the Windows device names (`CON`, `PRN`, `AUX`, `NUL`,
  `COM1`-`COM9`, `LPT1`-`LPT9`, `CONIN$`, `CONOUT$`, any case, any extension) are
  `NO_DATABASE`. A database the baseline Python implementation accepts with such a name cannot be
  shared until it is renamed.
- **`applied_since`** is bounded in SQL by an instant, never text (ADR-STORE-0004):
  `applied_epoch >= ?`, or, for an applied entry with no epoch, its time
  `COALESCE(applied_at, updated_at)` read by `unixepoch()` in the query; the two are
  separate index range reads joined by `UNION ALL` (`APPLIED_SINCE_SQL`, ADR-STORE-0004).
  **No expression index.** No index holds a
  function, `unixepoch()` included: an index on `unixepoch(..)` would make the
  file's schema unreadable, and every journal write fail, for a baseline Python
  implementation linked against SQLite older than 3.38 (Ubuntu 22.04 ships 3.37.2). The epoch
  is a plain column (ADR-STORE-0004) so that plain partial indexes serve the query.

Consequences: rows and memberships stay consistent across a prune,
rebuild or sync of the same file by the baseline Python implementation (tests `store.rs`; the
vendored `compat.rs` run was removed in sprint b-9, ADR-STORE-0006, and the format golden pins
the file).
Baseline Python implementation journal args that a-1's `Op::parse` refuses (for example
`{"add_labels": []}`, ADR-MODEL-0001) read as `BAD_ARGS` naming the entry.

## ADR-STORE-0003: One connection per process, and the store's own failures

**Status:** Approved (lead ruling, bc-lead, 2026-10-24); failure mapping amended for a-1 amendment 1 (`STORE_FAILED`); revised by fix-a-4-2 (lead ruling, bc-lead, 2026-10-24); amended by a-7 (lead ruling S34, bc-lead, 2026-10-24: `ConfigLoadError::code` and `ConfigLoadError::fix`, see the amendment below; its codes and exhaustiveness revised by lead rulings S37 and S38, fix-a-7-12; `BeadsDirOverride` and `BeadsDirError` added by lead rulings S48 and S49, fix-a-7-15, see the second amendment below); amended by ADR-BDC-0014 (the one connection is shared with `CacheScheduleStore`, behind one mutex, so `SqliteStore` is `Send + Sync`; the `Cache` that owns it stays `!Sync` by its own marker, ADR-CORE-0001; B7Q1-025)

Context: NFR-BDC-0007 allows one connection to the cache file per process.
The store can fail on its own (an SQLite error, a file that cannot be
created, a stored value that does not decode); a-1 amendment 1 gives those
failures their own code, `BD_CACHE.STORE_FAILED`, carrying the underlying
error as its source.

Decision:
- `SqliteStore::open_at` opens the file, then claims its canonical path
  (symlinks and `.` segments resolved) in a process-wide set (a
  `Mutex<BTreeSet<PathBuf>>`, released when the store drops); a second open
  of the same file in the same process, under any path that resolves to it,
  is refused and its connection closed before it reads or writes. Known
  limit: `canonicalize` resolves symlinks, not hard links, so a hard link to
  the cache file is a second path with its own claim; do not hard-link the
  cache file.
- The store's own failures are `BD_CACHE.STORE_FAILED`
  (`CacheError::store_failed`): `detail` names the step and the file, and
  the underlying error (rusqlite, I/O, `serde_json`) is kept as the error's
  `source` when there is one. `STORE_FAILED` has no source for: any stored
  value that does not decode or is inconsistent (`row_json`, an edge or
  scope kind, an id, timestamp or phase name, journal fields, the ready
  base, an `outage_since` without `outage_error`), each naming the entry
  and never skipped; and a journal mode SQLite will not set to WAL. A
  refused one-connection claim (NFR-BDC-0007) is not a store failure: it is
  `BD_CACHE.STORE_IN_USE` (PE-RBP-F008, ADR-MODEL-0002 amendment), whose fix
  says to close or reuse the other handle, since the file is fine. A type-conversion error
  rusqlite raises while reading a column keeps that rusqlite error as its
  source (`failed`); a value the store's own validation refuses after
  reading has no source (`corrupt`). `NO_DATABASE` means only missing or
  invalid `metadata.json` (REQ-BDC-0102); an I/O or JSON error reading it is
  kept as its source and its text stays in the detail, and a permission-denied
  read says so in the detail and the fix instead of the `bd init` advice
  (PE-RBP-F014).
  Journal text that no longer parses keeps `Op::parse`'s own code
  (`BAD_OP` / `BAD_ARGS` / `BAD_PRECONDITION`) with the entry's seq. One
  module makes the mapping: `error::failed` (with a source) and
  `error::corrupt` (without).
- `ConfigLoadError` (`load_repo_config`) carries its cause one way only: as
  `Error::source`. Its `Display` names the file and the fix, without the
  cause, so a reporter walking the source chain prints the cause once. Its
  code and fix are the amendment below.

Consequences: a caller tells a broken cache file (`STORE_FAILED`) from a
workspace without bd metadata (`NO_DATABASE`), and walks the source chain
with `Error::source`.

### ADR-STORE-0003 amendment (a-7, S34)

**Status:** Approved (lead ruling S34, bc-lead, 2026-10-24); codes moved out of the
`BD_CACHE.` namespace by lead ruling S37 (ARCH-801) and `#[non_exhaustive]` removed by
lead ruling S38 (RBP-F044, QA8-003, ARCH-808), bc-lead, 2026-10-24, fix-a-7-12;
amended by ADR-BDC-0013 (sprint b-7): `store_config_bad_scope` is a `scopes` entry or a
`[[scope]]` name that is not a valid `ScopeName`, or a `[[scope]]` filter that is refused, and
its fix states `ScopeName::RULE`; a valid `scopes` entry is a phase-a scope, never an error

Context: `bd-cache-sync`'s `ComposeError` kept its own copy of the code and fix of
each way `.beads/bd-cache.toml` fails to load (RBP-F040). Moving them next to the type
(fix-a-7-6) made them store API, but recorded them by rewriting the Decision above in
place (ARCH-701), and the store then emitted the sync crate's `sync_config_*` codes,
a consumer's namespace (ARCH-702, RBP-F043). S34 first gave them `BD_CACHE.CONFIG_*`
codes; but every `BD_CACHE.*` code is a `CacheError` code (REQ-MODEL-0003, REQ-BDC-0803),
and `ConfigLoadError` is not a `CacheError` (ARCH-801, S37). A consumer's wildcard arm
over the `#[non_exhaustive]` enum mapped any later variant to an existing code with no
compile-time check (RBP-F044, QA8-003, ARCH-808, S38).

Decision:
- `ConfigLoadError::code` and `ConfigLoadError::fix` are public store API: one stable
  code and one fix text per variant, and `Display` states that same fix after `fix:`.
- The codes are store-owned and lowercase (S37): `store_config_unreadable` (`Read`:
  the file exists but cannot be read), `store_config_invalid` (`Parse`: bad TOML, an
  unknown key or a wrong type) and `store_config_bad_scope` (`Scope`: a `scopes` entry
  is not a phase name; its fix states `PhaseName::RULE` [now `ScopeName::RULE`, ADR-BDC-0013]). They are **not `CacheError`
  codes** (the `BD_CACHE.*` namespace belongs to `CacheError` alone) and **not
  CLI-contract codes**: no CLI reply carries them; a consumer that reports a
  configuration failure reports its own code.
- `ConfigLoadError` is exhaustive, not `#[non_exhaustive]` (S38): each consumer matches
  every variant, with no wildcard arm.
- A consumer with codes of its own maps the variants at its own boundary; the store
  names no consumer's codes. `bd-cache-sync` keeps its `sync_config_*` codes by mapping
  `ConfigLoadError` variants in `ComposeError` and uses `fix()` as the recovery text.
  `bd-cache-py` maps the variants to its own exception kinds and does not use `code()`.

Consequences: changing a code or a fix text changes store API, and the tests that pin
them (`tests/location.rs`: `repo_config_is_parsed_and_unknown_keys_refused`,
`unreadable_repo_config_is_an_error_not_the_default`; the `ConfigLoadError::code`
doctest). A new variant needs a code and a fix here, and a mapping in each consumer;
the mechanism that enforces the mapping is the compiler (S38): because the enum is
exhaustive and the consumers' matches have no wildcard arm (`bd-cache-sync`'s
`ComposeError` code mapping, `bd-cache-py`'s `From<ConfigLoadError> for OpenError`), a
new variant is a compile error (`E0004`, non-exhaustive patterns) in each consumer
until it is mapped. Adding a variant is therefore a breaking change to store API.

### ADR-STORE-0003 amendment (a-7, S48/S49): one validated `$BEADS_DIR`

**Status:** Approved (lead rulings S48 and S49, bc-lead, 2026-10-24, fix-a-7-15;
QA10-001, RSH-038, RBP-F047, RBP-F048; per-platform wording by lead ruling S50, RSH-039)

Context: S44 normalized `$BEADS_DIR` (empty is unset, relative is made absolute) inside
`bd-cache-sync`'s `compose_with` only, and the store still took a raw `Option<&OsStr>`,
so another pairing of the store and a `bd` child could name two directories again
(RBP-F047). A value whose working directory could not be read was kept relative,
which reintroduced that split and dropped the I/O error (QA10-001, RSH-038, RBP-F048).

Decision:
- The rule lives in one validated type, `BeadsDirOverride` (a newtype over an absolute
  `PathBuf`). `BeadsDirOverride::new(Option<&OsStr>)` is the one fallible constructor:
  unset or empty is `Ok(None)`; any other value is made absolute with
  `std::path::absolute` against the process's working directory. On Unix that joins a
  relative path with the working directory and resolves nothing (no `..`, no link;
  only `.` components and repeated separators drop out, as `Path::components` does);
  on Windows it calls `GetFullPathNameW`, which also resolves `.` and `..` textually,
  without touching the file system (S50). `BeadsDirOverride::from_env` is `new` over
  the process's `$BEADS_DIR`. `as_path` and `as_os_str` give the value to the store and
  to a child.
- It fails closed (S48): a value that cannot be made absolute is a `BeadsDirError`,
  never a relative fallback. `BeadsDirError` names the value in `Display` and carries
  the `io::Error` only as `Error::source`; `value()` and `into_parts()` hand both to a
  consumer that maps it to an error of its own, and `BeadsDirError::new` lets a
  consumer build one to test that mapping.
- `SqliteStore::open_with`, `CacheLocation::resolve_with` and `beads_dir` take
  `Option<&BeadsDirOverride>` instead of `Option<&OsStr>` (a signature change of store
  API; `bd-cache-store` is not a btit API).
- The environment-reading paths, `SqliteStore::open` and `CacheLocation::resolve`, build
  the override with `from_env`. An unresolvable environment value is
  `BD_CACHE.NO_DATABASE`, its detail naming the value and the I/O error, before any file
  is read: the beads directory cannot be located, which is what `NO_DATABASE` reports.
  Its detail ends with the real remedy, "set an absolute BEADS_DIR or run from a
  readable working directory" (PE-RSH-043), since the code's `bd init` fix does not
  address it; the I/O error stays text only, so a permission-denied working directory
  does not select the fix for an unreadable `metadata.json`. `bd-cache-py`, which opens through `SqliteStore::open`, raises it as it raises
  any `NO_DATABASE`.
- `bd-cache-sync`'s `compose_with` builds the override once and passes the same value to
  `SqliteStore::open_with` and its `as_os_str()` to `BdCli::with_child_var`; it maps a
  `BeadsDirError` to its own `ComposeError::BeadsDir` (`sync_beads_dir_unresolvable`).

Consequences: the store and every `bd` child of a composition cannot be given two
different directories, since both take the one value the type holds. A consumer that
has a raw value calls `BeadsDirOverride::new` and handles its error. Evidence
(`src/location.rs` unit tests): `an_unset_or_empty_beads_dir_is_no_override`,
`a_relative_beads_dir_is_made_absolute_against_the_working_directory`,
`an_absolute_beads_dir_is_kept` and
`a_beads_dir_that_cannot_be_made_absolute_is_an_error_with_its_cause` (the
`absolute` step injected to fail; also the `NO_DATABASE` mapping of the
environment-reading paths); the `BeadsDirOverride` doctest; `tests/location.rs`
(`test_beads_dir_env_names_the_database` through the type).

## ADR-STORE-0004: A per-bead index of the ready base, and an index for the journal check (a-7 amendment)

**Status:** Approved (lead ruling, bc-lead, 2026-10-24, fix-a-7-2; journal indexes revised by lead ruling S18; read-path dating approved by lead rulings S25/S26, see below; NFR-BDC-0001's condition stated by lead ruling S31, see Remaining latency; floor invariant restated per rise, restatement only, no decision change (QA7-001, fix-a-7-10)); amends ADR-STORE-0001 (the extension tables, columns and indexes)
and ADR-STORE-0002 (what is read as one snapshot, what a foreign writer may leave, and the
Concurrency bullet: the journal reads may write, as the exception noted there)

Context: `CacheStore::base_entry` and `has_entries_since` (ADR-MODEL-0003's a-7
amendment, ADR-CORE-0206) must not cost more as the scope or the journal grows.

Decision:
- An additive table `ready_base_blocked(scope, bead, blocked_by_json)`
  (`WITHOUT ROWID`, primary key `(scope, bead)`) holds one row per blocked bead,
  written in the same transaction as `ready_base` by `replace_ready_base` and
  deleted with it by a rebuild and by `prune_scope`; a nullable column
  `ready_base.indexed` is 1 when the index belongs to the stored base. The
  blockers are merged in order without repeats; a bead without blockers has no row.
- `base_entry` runs in one read transaction (`SqliteStore::read`), so the head
  and the bead's row are one snapshot even while another process replaces the
  base. A base with `indexed` NULL is read whole, inside the same transaction.
- **No function in any index.** The baseline Python implementation may be linked against an SQLite older
  than 3.38 (Ubuntu 22.04 ships 3.37.2), which has no `unixepoch()`. Such a build
  cannot evaluate an index whose key uses it: it would fail to use the file's schema
  and every `journal` write of that writer would fail. The a-7 build that added
  `journal_applied_at ON journal(unixepoch(applied_at))` is therefore withdrawn: open
  runs `DROP INDEX IF EXISTS journal_applied_at`, so a file written by that build
  is made readable again.
- **`journal.applied_epoch`**, a nullable `INTEGER`: the Unix seconds of the instant
  `SqliteStore::apply_with_readback` records in `applied_at`, written in the same
  `UPDATE` that sets `state = 'applied'`. Two plain partial indexes serve the check:
  `journal_applied_epoch ON journal(applied_epoch) WHERE state = 'applied'`, and
  `journal_applied_unknown ON journal(seq) WHERE state = 'applied' AND applied_epoch IS NULL`
  (entries with no epoch).
- **Backfill** (`BACKFILL_APPLIED_EPOCH`, an `UPDATE` through `journal_applied_unknown`):
  for each applied row with no epoch, `applied_epoch = unixepoch(COALESCE(applied_at, updated_at))`,
  where SQLite can read that time. This process's bundled SQLite evaluates
  `unixepoch()`; no index mentions it. The baseline Python implementation writes `%Y-%m-%dT%H:%M:%SZ`,
  which SQLite reads. Open always runs it, in the open transaction.
- **Read-path dating (S25, S26).**
  **Status:** Approved (lead ruling S25/S26, bc-lead, 2026-10-24).
  S25 had `has_entries_since` and `applied_since` date on every read that found an
  entry to date; S26 replaces that with a threshold, so a small burst of entries
  the baseline Python implementation applies while the store is open never puts a WAL commit on the `get`
  path. Before answering, each of the two reads counts the undated entries above the
  floor of known unreadable ones (`UNDATED_ABOVE_SQL`, a `journal_applied_unknown`
  range read that evaluates no function, capped at the threshold + 1; one index probe
  in a healthy file). At or below `READ_DATING_THRESHOLD` (2000) nothing is written and
  the read walks the undated entries. Above it the read first runs the backfill as one
  autocommit `UPDATE` with the busy timeout set to zero (`BusyWait` at zero, a drop guard
  that restores `BUSY_TIMEOUT`, also on unwind), so it never waits for the write lock; a
  writer holding the lock, or a read-only file, leaves the entries undated for now, the
  read answers the same from them, and the next read tries again. The answer never
  depends on whether the `UPDATE` ran.
  *Measurements* (release build, Apple silicon, 1000-bead synced scope, cached `get` of
  a bead with a stored base, median of 500 gets; probe in the a-7 fix-5 QA scratchpad):
  idle `get` 21-23 us; with N undated entries walked, not dated: 500 → 62 us, 1000 → 101 us,
  1500 → 140 us, 2000 → 175-183 us (about 0.08 us per entry). The dating commit itself
  costs a first `get` 2.2-3.1 ms at 2001 entries, 3.2-5.4 ms at 3000, 5.2-11 ms at 5000,
  20-31 ms at 20 000 (QA's earlier run of the S25 build: 2.9 ms at 1000, 9.5-33 ms at 5000,
  21-25 ms at 20 000), after which `get` is back to 22 us. 2000 keeps the walked `get` under
  0.2 ms, a fifth of NFR-BDC-0001's 1 ms with room for a machine several times slower,
  while the commit it avoids costs 2 ms or more, ten times the walk.
  *Remaining latency against NFR-BDC-0001* (lead ruling S31: NFR-BDC-0001 now states
  the condition, at most `READ_DATING_THRESHOLD` undated entries and no foreign writer
  holding the write lock, and names these excursions): above the threshold, the one `get` that dates
  is a one-off excursion past 1 ms (2-31 ms as measured, growing with the burst); every
  later `get` is back under it. While another writer holds the write lock over more than
  2000 undated entries, each `get` walks them (1.3 ms median at 20 000) until the lock
  is free. A burst at or below the threshold costs at most the walk, about 0.2 ms, and
  writes nothing.
- **Unreadable entries on the read path (QA5-002).** The store keeps a floor of known
  unreadable entries. The count above starts at the floor, so those entries are not
  walked by the count on every call. The floor rises after a dating or a new warning,
  through the unreadable entries above it and never past an applied entry the dating
  can date (`FIRST_DATEABLE_ABOVE_SQL`). **The invariant holds per rise (QA7-001):** a
  rise from an old floor to a new one passes only the entries between the two (above
  the old, at or below the new), and every one of those that was applied and undated
  when the floor rose had an unreadable time, so no dateable entry above the old floor
  is hidden from the count. Entries already below the old floor are not examined again
  by a rise: the floor says nothing about them, and one of them may be readable (the
  case below), also after later rises. The store also remembers the highest seq it has examined:
  each read looks at the undated entries above it only (`LAST_UNDATED_SQL`,
  `UNDATABLE_BETWEEN_SQL`), so each entry's time is read there once, and warns once
  for each new highest undatable seq (the open warns about all of them and starts both
  marks there).
  **Entries applied below the floor (QA6-001).** An entry still pending when the floor
  rose above its seq, which the baseline Python implementation applies later without an epoch, sits below
  the floor: it is not in the threshold count and is not examined for a warning, and a
  later rise (one driven by a warning alone included) does not examine it either. It is
  answered correctly, as every undated entry is (the journal reads do not use the
  floor, and read its own time), and it is dated by the next dating, past the
  threshold or at the next open, because the backfill dates every readable entry
  whatever its seq. Until then reads walk that one
  entry. Capping the floor below the lowest pending seq was rejected: while an old
  entry stayed pending (during an outage, for hours), every unreadable entry above it
  would be back in the count, and past the threshold every read would try the dating
  again, the per-read walk and write this floor removed. Pinned by
  `a_pending_entry_applied_below_the_floor_is_answered_and_dated_by_the_next_dating`
  (unit), which also raises the floor a second time from a warning alone after the
  entry is applied below it: the entry stays undated and answered by its own time
  until the next dating dates it (QA7-001).
- **Unreadable times count as touched.** A row whose `COALESCE(applied_at, updated_at)`
  SQLite cannot read as a time keeps a NULL epoch, stays in `journal_applied_unknown`,
  and counts as applied since any instant (`COALESCE(... >= ?1, 1)`). Reporting
  activity that did not happen only costs a fresh read; missing it would serve a
  stale ready answer. `applied_since` agrees with it. The cost: while such a row exists,
  every cached `get` of a bead with a stored base takes the adjusted path (the whole base
  is recomputed). So open, after the backfill, logs a warning naming the seqs of the
  applied entries still undated (the first 20, their count and the highest), and the read
  path warns about new ones, once each (above). **Operator fix:** find the
  entry (`SELECT seq, idem_key, bead, updated_at FROM journal WHERE seq = <seq>`) and either
  resolve it (`UPDATE journal SET state = 'resolved' WHERE seq = <seq>`, which takes it out
  of the applied set) or delete it (`DELETE FROM journal WHERE seq = <seq>`); an applied
  entry is history only, so neither loses a pending write. Setting its `updated_at` to a
  real time works too; the next read dates it.
- **The pre-existing miss, fixed.** The baseline Python implementation's `_mark` sets only `state` and
  `updated_at`, so an entry it applied has `applied_at` NULL. Before this fix
  `applied_since` and `has_entries_since` compared `applied_at` alone and so missed
  every Python-applied entry. Its time is now `COALESCE(applied_at, updated_at)`
  (backfilled, or read in the query), and the miss is closed.
- `has_entries_since` is three `EXISTS` lookups (`HAS_ENTRIES_SINCE_SQL`): `journal_pending`
  for pending entries; `journal_applied_epoch` for entries with an epoch; and
  `journal_applied_unknown` for those without. The last two are named with `INDEXED BY`,
  because the planner otherwise scans the applied rows through `journal_pending`. The
  first two cost an index probe each whatever the history; the third walks the entries
  without an epoch, so its cost is the number of those that are older than `at`. The
  backfill above keeps that number at zero (the entries with an unreadable time stop the
  walk at once: they count as since), and the read-path dating keeps it at or below
  `READ_DATING_THRESHOLD` while the store is open (S26), so the check stays bounded; it is
  not bounded for entries the dating could not yet date (the write lock was busy).
- `applied_since` is two range reads joined by `UNION ALL` and ordered by seq
  (`APPLIED_SINCE_SQL`): `journal_applied_epoch` for `applied_epoch >= at`, and
  `journal_applied_unknown` for the undated entries. One `WHERE` with an `OR` of the two
  (the earlier form) lets neither partial index serve it, so it read every applied entry.
- **A missing hinted index.** An index another writer dropped makes `INDEXED BY` an error
  (`SQLITE_ERROR`, `no such index`; matched on the code and the message). SQLite has no
  more specific code for the case, so the detection relies on the message prefix
  `no such index` that SQLite's `INDEXED BY` failure carries (REQ-QA-503); the test
  `the_entries_since_check_survives_a_dropped_index` drops the indexes and so pins that
  prefix for the bundled SQLite: a release that changed it would fail that test, not
  production silently. The store then
  logs one warning, remembers it, and from then on asks the unhinted form of each journal
  read (`HAS_ENTRIES_SINCE_UNHINTED_SQL`, `APPLIED_SINCE_UNHINTED_SQL`, the backfill's and the
  read-path dating's own queries):
  the same question, correct, slower on a long history. The hints are not tried again
  until the next open, which recreates the indexes. Tests assert the plans of the hinted
  queries, their SQL work in VM steps, and that the fallback is not retried.
- **Baseline Python implementation compatibility** (read in the v3
  baseline): it never creates,
  reads or writes `ready_base`, `ready_base_blocked` or `scope_member`. Its
  rebuild deletes `edges`, `beads` and `sync_state` (lines 359-361); its prune
  deletes a phase's `edges`, `beads`, `journal` and `sync_state` rows (611-614);
  every other write is `INSERT OR REPLACE` on `meta` and `beads`. So a stored
  base and its index survive its rebuild and prune together and stay in
  agreement (ADR-STORE-0002: the next sync replaces them). Were a foreign writer to
  `INSERT OR REPLACE` a `ready_base` row without the new column, `indexed` would
  reset to NULL and the left-over index rows would be ignored; an in-place
  `UPDATE` of `blocked_json` is the one write the index could not see, and no
  known writer does it. The tests below pin each case.
- A file written before this ADR (no table, no column) opens unchanged
  (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN` when absent) and its
  base reads whole until the next replace indexes it; its applied entries are dated by the backfill. The file stays at
  `user_version` 3.

Consequences: the contract suite's `base_entry_rules` and `has_entries_since_rules`
pin both methods to their provided bodies for every store; the store tests
`a_python_style_rebuild_or_prune_leaves_the_base_and_its_index_in_agreement`,
`a_base_replaced_by_another_writer_is_read_from_its_blob_not_from_a_stale_index`,
`a_file_from_before_the_ready_base_index_opens_and_migrates_on_the_next_replace`
and `the_entries_since_check_uses_indexes_and_ignores_a_long_history` check the
compatibility claims; `entries_python_applies_while_open_are_dated_by_the_next_check`,
`the_check_does_not_wait_for_the_write_lock_to_date_entries`,
`a_small_burst_is_walked_and_not_dated_until_past_the_threshold` (S26: no commit at or below
the threshold, `PRAGMA data_version`), `an_unreadable_entry_does_not_hide_earlier_undated_ones_from_the_dating`,
`applied_since_reads_both_partial_indexes_and_no_history`,
`the_entries_since_check_survives_a_dropped_index` (store tests),
`the_open_finds_the_applied_entries_it_could_not_date`,
`undatable_entries_written_while_open_are_warned_once_and_not_walked_again` (unit, QA5-002),
`the_floor_stops_one_below_the_first_dateable_entry` (unit, QA5-002: the floor is F - 1),
`the_dating_update_runs_with_no_busy_timeout_and_restores_it` (unit, QA5-003: the busy
timeout sampled inside the `UPDATE` by a temporary trigger is 0, and is back afterwards;
it replaces the timed `a_write_after_a_skipped_dating_waits_for_the_lock_again`, removed
for FTQ-022),
`a_pending_entry_applied_below_the_floor_is_answered_and_dated_by_the_next_dating` (unit,

|---|---|---|

the schedule would not move with the cache).

Consequences: a v3 reader that does not know an extension still reads and writes the file.
Further extensions need a later ADR.

Implementation notes (sprint b-7):
- `schema.rs` adds the five columns through `EXTENSION_COLUMNS` and the two tables through
  `EXTENSION_TABLES`; `sc_cron_schedule` is sc-cron's version-2 DDL with sc-cron's own limits
  (`sc_cron_schedule_table`), and the `meta` row is written with `INSERT OR IGNORE`, so a file
  holding another version keeps it and `CacheScheduleStore` refuses it
  (`StoreErrorKind::SchemaMismatch`). `tests/format_golden.rs` pins the whole schema
  (`tests/fixtures/format-golden.txt`) and checks that a v3-only file
  (`tests/fixtures/v3-schema.sql`) gains every extension at `user_version` 3 and that a v3
  reader still reads and writes the extended file.
- `scope.kind` stays `phase` for every row (existing names stay); `scope.filter` alone tells
  a filter scope (the filter's JSON) from a phase-a scope (NULL), so a v3 reader that knows
  only `kind = 'phase'` reads every row this build writes; a row of another kind does not
  decode (`tests/phase_b_store.rs`, the data-level check, B7Q1-007). A v3 `phase` column is
  read as a phase-a scope's membership only, never a filter scope's of the same name
  (`in_scope!`, `RECONCILE_MEMBERSHIP`).
- The four registry calls share one registration body (`register`, with an add-or-set,
  if-absent, add or set mode) and `scope_remove` and `prune_scope` one prune body; a
  registration past `MAX_REGISTERED_SCOPES` is `BAD_ARGS`.
- `ingest_scope` trusts the snapshot's limits (the snapshot owns them, B7Q1-018); it encodes
  every row before its one `BEGIN IMMEDIATE`; in the transaction it refuses an unregistered
  scope (`SCOPE_UNKNOWN`) and reads the registered filter, replaces the scope's memberships
  with the snapshot's rows the status criterion admits, stores rows unforced, writes the
  ready base restricted to the members, records an ok sync state and the revision. A failure
  half way rolls back whole (`tests/phase_b_store.rs`).
- `record_sync_result` applies the `failing_since` lifecycle to the stored sync state in one
  write transaction; `record_sync` never writes `notified_since`.
- The lease and the hook state are one-row tables (`id = 1`); `lease_take` refuses an
  `expires_at` not after now or past `MAX_LEASE_TTL`, decides free, live or expired inside
  one write transaction, and replaces a row that does not decode (with a warning) instead
  of failing every later take. `hook_failed` keeps at most `MAX_HOOK_ERROR_BYTES` of the
  error.

## REQ-CRON-0001: Parse before write

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-2); amended by b-6
(five-field expressions are accepted, REQ-CRON-0015)

Schedule input is validated before anything is stored, once, by type:
`ScheduleName` (1 to `MAX_NAME_LEN` = 128 bytes, no surrounding whitespace,
no control characters), `CronExpr` (at most `MAX_EXPR_LEN` = 256 bytes,
parsed), `RunTimeout` (1 ms to `MAX_TIMEOUT` = 24 h) and a payload of at
most `MAX_PAYLOAD_BYTES` = 64 KiB of compact JSON, checked by
`ScheduleSpec::new`, `Scheduler::start` and the store with one rule.
`Scheduler::start` also refuses an expression with no future occurrence.
An expression that does not parse or has no future occurrence is
`CronError::BadExpression`; any other invalid field or
exceeded limit is `CronError::InvalidSpec`. Nothing is written either way.
The number of active schedules is not capped: the caller creates every
schedule, and each row is bounded by the limits above.

**Refines:** ADR-BDC-0006 (expression parse before write)

## REQ-CRON-0002: Next-run computation in UTC

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-2); amended by b-6
(five-field expressions, REQ-CRON-0015)

The grammar is the `cron` crate's in UTC: six or seven fields, seconds
first, year optional, or `@yearly`, `@monthly`, `@weekly`, `@daily`,
`@hourly`; and, from b-6, standard five-field crontab (REQ-CRON-0015). A schedule's next run is the first `occurrence + jitter` strictly
after now, so a restart inside an open jitter window still fires that
occurrence. The next run is stored after every tick. An expression with no
further occurrence ends the schedule with reason `no future occurrence`.

**Refines:** ADR-BDC-0006 (next-run computation)

## REQ-CRON-0003: Jitter

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-2)

`start` draws one jitter per schedule from the injected `JitterSource`,
in `[0, min(period / 2, 30 min))`, where the period is the gap between the
expression's next two occurrences. The jitter is stored and kept for the
life of the schedule, and is drawn again only when the name is restarted.

**Refines:** ADR-BDC-0006 (jitter)

## REQ-CRON-0004: Missed-tick replay per policy

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-2)

An occurrence is missed when the worker sees it only after the occurrence
following it is also due: the process was down or the host was suspended.
Under `MissedTickPolicy::Coalesce` (the default) all missed occurrences are
replayed as one run as soon as the worker sees them. Under
`MissedTickPolicy::Skip` they are dropped. A run that is late but not missed
always runs. A backlog is never run one by one. The schedule then continues
from its next future occurrence.

**Refines:** ADR-BDC-0006 (missed-tick replay)

## REQ-CRON-0005: Stop check and per-run timeout

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-2); amended by b-6 (the
three-way answer, ADR-CRON-0007); amended by ADR-CRON-0009 (the `Stop` alias is removed)

Before every run the worker asks the stop check: `Job::should_stop`, or for a
Python target the `cron.stop` hook (REQ-CRON-0013). It answers
`StopDecision::Continue`, `Disable(reason)` or `Delete(reason)`, and for
`Disable` and `Delete` nothing runs. `Disable` keeps the schedule active but
not enabled (REQ-CRON-0014) and records the reason as the last outcome,
`Refused(reason)`. `Delete` ends the schedule with that reason, as `Stop`
did; its row is kept as the ended record and the name can be started again.
`StopDecision::Stop(reason)` remains as an alias of `Delete(reason)` for
callers written against the earlier contract. A stop check that cannot answer
skips that run and leaves the schedule active and enabled: a panic is recorded
`Failed`, a run past the timeout `TimedOut`, and for a Python hook a failure
to start, a non-zero exit or a reply that is not one of the three actions is
recorded `Failed`. Stop check and run share the
schedule's timeout. The job receives the deadline, on the clock's monotonic
timeline. A run still going at the deadline is cancelled and recorded as
`RunOutcome::TimedOut`, and the next tick fires on time. The worker measures
the deadline on the monotonic timeline, so a wall-clock jump never times a
run out early. Cancellation is cooperative, at the run's next `.await`; the
hard timeout guarantee needs a multi-thread runtime and a job that never
blocks a runtime thread (documented on `Job`).

*Amended by ADR-CRON-0009 (Rand, 2026-10-26): `StopDecision::Stop` is removed in sprint b-8; `Delete(reason)` is the only way to end a schedule from its stop check.*

**Refines:** ADR-BDC-0006 (stop check before every run), ADR-CRON-0007;
constrained by REQ-BDC-0703, NFR-BDC-0004

## REQ-CRON-0007: Generation fencing

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-2); amended by b-6

Every schedule has an id that is stable for its name and a generation that
rises each time an ended name is started again. Every run-state write
(`record_run`, `set_next`, `stop`, `disable`) names `(id, generation)` and
changes nothing, returning `false`, unless that pair is the active schedule.
The store enforces this, so it holds between processes that share the
database file: a process that kept an older generation changes nothing
whichever process restarted the schedule. A run
from an older generation therefore cannot record its result. A fenced write
makes the worker reload at once.

**Refines:** ADR-BDC-0006 (`(id, generation)` fencing)

## REQ-CRON-0012: Bounded shutdown

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-2)

`WorkerHandle::shutdown(deadline)` stops ticking and waits for each in-flight
run until that run's own deadline, recording its outcome. If the shutdown
deadline passes first, the worker and its runs are aborted and record
nothing. The worker checks for shutdown between slots, so no new run starts
after shutdown is requested; a shutdown that arrives during a reload still
keeps every unchanged in-flight run for the drain. Dropping the handle also stops the worker, but
the drain then runs detached; callers await `shutdown` to know outcomes were
recorded. A scheduler runs at most one worker at a time. `Scheduler::start`
and `stop` are synchronous store calls; `start_async` and `stop_async` run
them on tokio's blocking pool.

**Refines:** ADR-BDC-0006

## REQ-CRON-0013: Python hook target

**Status:** Approved (Rand's rulings, 2026-10-25)

A schedule's worker runs a `HookTarget`: a Rust `Job`, or a Python module
(`HookTarget::Python(PythonHook)`). A Python target runs as
`<interpreter> -I -m <module>` from a fresh temporary working directory, once
per event, with one JSON object on stdin:
`{"protocol": "sc-cron.hook.v1", "event": "cron.tick" | "cron.stop",
"schedule", "payload", "deadline"}`, where `schedule` is the schedule's name,
`payload` is its payload as stored and `deadline` is the run's deadline as a
UTC instant. The worker sends `cron.stop` before every run, and `cron.tick`
for the run if the stop check said to continue; both carry the same deadline.
A `cron.stop` hook answers on stdout with
`{"action": "continue" | "disable" | "delete", "reason": "..."}` (REQ-CRON-0005;
`reason` is required for `disable` and `delete`). A `cron.tick` hook that exits
0 is `RunOutcome::Ok`, any other exit is `Failed`.

Every hook a schedule starts, `cron.tick` and `cron.stop` alike, is killed,
with every process it started, at the schedule's timeout capped by the time
left before the run's deadline (a Unix process group or a Windows job object
carries the kill, and it also happens if the run is cancelled). A run whose
deadline has passed starts no hook. Each of stdout and stderr is kept up to
`MAX_HOOK_OUTPUT_BYTES` (64 KiB) and the rest is read and discarded, so a hook
that floods a pipe is neither blocked nor allowed to grow memory. The
interpreter is an absolute path or a bare command name, and the module a dotted
path of ASCII identifiers of at most 256 bytes, both checked once when
`PythonHook::new` builds the target. A hook that cannot be started is
`CronError::HookFailed` (`HOOK_FAILED`) from `PythonHook::invoke`, and a
`Failed` outcome from the worker.

This runner is also the one `bd-cache-sync` (sprint b-8) uses for the
consumer's Python sync row (`PythonHook`), and its post-sync hook runs through
this crate's exported supervisor (REQ-CRON-0018), so the kill described here
enforces NFR-BDC-0004 for both (*amended by ADR-CRON-0009*).

**Refines:** ADR-CRON-0001, ADR-CRON-0008; **constrained by:** NFR-BDC-0004,
REQ-CRON-0010 (time is injected), REQ-CRON-0011

## REQ-CRON-0014: Enabled flag

**Status:** Approved (Rand's rulings, 2026-10-25)

Each schedule has an `enabled` boolean, stored in an `enabled` column that
defaults to 1. `Scheduler::set_enabled(name, enabled)` (and `set_enabled_async`)
updates only that column of the active schedule with that name, so its id,
generation, expression, payload, timeout, jitter and run state are unchanged;
a name with no active schedule is `CronError::NotFound` (`NOT_FOUND`). A
disabled schedule never fires: the worker keeps no slot for it, and its stored
next run is left as it was. A run in flight when the schedule is disabled is
cancelled and records nothing. Enabling resumes the same schedule; a run that
came due meanwhile counts as missed and is handled per the `MissedTickPolicy`
(REQ-CRON-0004). The change reaches this scheduler's worker at once. A worker
in another process, or on another scheduler, gets no signal, and a schedule it
holds no slot for (new, disabled, ended) wakes nothing. So the worker reloads
the active schedules at least once per reload-poll interval on the injected
clock, whatever the rows are (`Scheduler::with_reload_poll`, default
`DEFAULT_RELOAD_POLL`, 30 s; values under 1 s are raised to 1 s). A schedule
started, restarted, enabled, disabled or stopped elsewhere is therefore
noticed at most one interval after the change is stored: a started or
restarted or re-enabled schedule gets its slot (a run that came due
meanwhile is handled per the `MissedTickPolicy`), and a disabled, stopped or
restarted-over schedule loses its slot and its run in flight is cancelled. A
disable or stop is also noticed earlier if its next tick comes first, because
`set_next` refuses a disabled or ended schedule and a refused write makes the
worker reload before it launches (REQ-CRON-0007). The bound holds while the
store can be read; a failed reload is retried with a backoff of 1 s doubling to
60 s (REQ-CRON-0007). A reload is one `list_active` query that keeps every
unchanged slot, so the poll costs one query per interval. A new or restarted
schedule is enabled, and a stop check can disable a schedule (REQ-CRON-0005).

**Constrained by:** REQ-CRON-0008 (the store reads no clock), REQ-CRON-0009
(`SCHEMA_VERSION` 2)

**Refines:** ADR-BDC-0006, ADR-CRON-0007

## REQ-CRON-0015: Five-field expressions

**Status:** Approved (Rand's rulings, 2026-10-25)

A standard five-field crontab expression (minute, hour, day of month, month,
day of week) is accepted, in UTC, and fires at second 0 of each matching
minute. It is read with crontab's meaning, not the `cron` crate's: the day of
week counts Sunday as 0 or 7 and Monday as 1 (names `SUN`..`SAT` are accepted,
and a range or step may be used), where the `cron` crate counts Sunday as 1;
and when both the day of month and the day of week are restricted (neither
field starts with `*`), a day matches if either field matches. A day-of-week
field outside this grammar (for instance `5L` or `1#2`) is
`CronError::BadExpression`; the six- and seven-field forms keep the `cron`
crate's grammar and numbering, and the `@` macros are unchanged. Fewer than
five fields remain `BadExpression`. The expression is stored as given.

REQ-CRON-0001 and REQ-CRON-0002

## ADR-CRON-0001: Generic job payload and an sc-cron error type

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-1)

Context: the scheduler `sc-cron` was extracted from ran its host's hooks: a
schedule carried a team name, a phase id, a module path, cwd, args and
`custom` data, a tick was a hook request, a reply's actions went to an action
dispatcher, and every failure was the host's error type. ADR-BDC-0006 requires
`sc-cron` to carry none of that.

Decision: a schedule's input is one opaque `serde_json::Value` payload
(at most `MAX_PAYLOAD_BYTES`), handed to a caller-supplied `Job` (`run`
with a deadline, `should_stop`) on every tick. The earlier scheduler's two
stop conditions (`Until` and the stop hook) become `Job::should_stop`, so a
time limit is a payload field the job checks. Outcomes are
`RunOutcome { Ok, Refused, Failed, TimedOut }`. Its hook-specific `Actions`,
`Malformed`, `ActionErr` and `Exit` fold into `Ok` or `Failed`. Failures are one `#[non_exhaustive] enum CronError` with a stable
`code()` (`BAD_EXPRESSION`, `INVALID_SPEC`, `ALREADY_ACTIVE`,
`STORE_FAILED`, `FENCED`) and `recovery()` text. A store failure is a
`StoreError`: a `StoreErrorKind` (`Busy`, `Corrupt`, `SchemaMismatch`,
`Unavailable`, `Other`), a context naming the operation and row, and the
backend's error kept as `Error::source`. No backend type appears in the
port. `Fenced` carries the id and generation it was refused for.

Amendment (sprint b-6): `CronError` gains `NotFound` (`NOT_FOUND`) and
`HookFailed` (`HOOK_FAILED`), and the payload can also be handed to a Python
module (ADR-CRON-0008).

Consequences: bd-cache-sync puts its scope and budget in the payload and
implements `Job`. A caller can retry on `Busy` and alert on `Corrupt`
without parsing text. A store outside this crate builds its errors with
`StoreError::new(..).with_source(..)`.

## ADR-CRON-0002: Clock carries monotonic time and sleeping

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-1)

Context: the sprint contract sketch gave `Clock` only `now()`. A worker that
can only read the time cannot wait for a manual clock to advance, and a
job's `Instant` deadline needs a monotonic timeline that a manual clock also
controls.

Decision: `Clock` also has `monotonic_now()` (default `Instant::now()`) and
`async fn sleep_until(target)`, as the earlier scheduler's `Clock` does. `SystemClock`
sleeps in slices of at most 30 s and re-reads the wall clock between them.
`ManualClock` moves both timelines together and never moves monotonic time
back. `jump_wall` steps wall time alone, to model an NTP step. Each park is
recorded with the time the sleeper saw, and `advance_settled` waits for a
park at the new time, so an earlier park cannot satisfy it.

Consequences: the trait uses `async-trait`. A job compares its deadline with
`Clock::monotonic_now`; under `SystemClock` that is `Instant::now`.

## ADR-CRON-0003: Persisted next run; missed ticks coalesce by default

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-1)

Context: the earlier scheduler recomputed every next run from now at startup,
so a tick missed across a restart was never replayed, while a tick missed
during a suspend fired once. ADR-BDC-0006 asks for missed-tick replay.

Decision: the store keeps `next_run_at`, written before each launch. An
occurrence is missed when the worker sees it only after the following
occurrence is also due. `MissedTickPolicy::Coalesce` (default) replays all
missed occurrences as one run. `MissedTickPolicy::Skip` drops them. A late
but not missed run always runs. The policy is set on the `Scheduler` and
applies the same way across restarts and suspends.

Consequences: a sync schedule catches up once after downtime instead of
waiting a full period. A run interrupted by a crash is not replayed, since
its next run was stored before launch.

## ADR-CRON-0004: One fixed jitter per schedule

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-1)

Context: the earlier scheduler stored a whole-second jitter per schedule and
spread it over offsets not held by other schedules with the same expression (a
product ruling there). The contract's `JitterSource::jitter(max)` returns a
`Duration`.

Decision: `start` draws one jitter in `[0, max)` with
`max = min(period / 2, 30 min)`, clamps an out-of-range draw to `max`,
truncates it to whole milliseconds and stores it. Every occurrence fires at
`occurrence + jitter`. The held-offset spreading is not carried over.
Random offsets spread load statistically, and intervals stay regular.

Consequences: two schedules with one expression may draw the same offset.
That is harmless, and a caller that cares can pick distinct names and
expressions.

## ADR-CRON-0005: The worker enforces run deadlines on the monotonic clock

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-1)

Context: a run must not delay the next tick, and a timed-out run must stop
working. With tokio timers inside the run task, a manual clock could not
drive timeouts, and the worker would not be the clock's only sleeper. A
deadline measured on the wall clock would be cut short by a forward
wall-clock jump.

Decision: each run's deadline is `monotonic_now() + timeout`, the same
`Instant` the job receives. The worker converts the remaining span to a
wall-clock wake time for `sleep_until`, then compares against
`monotonic_now()` before timing anything out. At the deadline the worker
aborts the run task and records `TimedOut`. Dropping an in-flight run (a
reload, a stop, a restart or an aborted worker) also aborts it, and an
aborted run records nothing. Cancellation is cooperative: the job passes
the deadline into any `spawn_blocking` work, which an abort cannot cancel.
A job must not block a runtime thread, and the hard timeout guarantee needs
a multi-thread runtime (documented on `Job` and in the crate docs).
Timeouts are `RunTimeout`: 1 ms to 24 h, in whole milliseconds.

Consequences: timeouts are testable under `ManualClock`, including a wall
jump. A job that blocks a runtime thread without yielding cannot be
cancelled; that limit is documented rather than worked around.

## ADR-CRON-0006: Implemented contract and store

**Status:** Approved (lead ruling 2026-10-24, a-3 QA-1); amended by ADR-BDC-0014 (`SqliteScheduleStore` is the standalone default; a caller may supply its own `ScheduleStore`) and ADR-CRON-0009 (`set_enabled_many` and `replace_and_set_enabled`)

Context: the contract sketch's `create(spec, created_at)` and `Schedule`
fields left nowhere to keep the jitter or first run, to read a run's outcome
back, or to read an ended schedule. Instants and names crossed the port as
raw strings, and were re-validated at each layer. Edition 2024 reserves
`gen`. NFR-BDC-0007 gives the cache file one connection per process.

Decision:

- Validated values: `Timestamp` (UTC, microsecond precision) for every
  instant on the port and in `Schedule`, rendered to text only at the SQL
  boundary. `ScheduleName`, `CronExpr` and `RunTimeout` are the one
  definition of a valid name, expression and timeout. The payload size has
  one check, shared by `ScheduleSpec::new`, `Scheduler::start` and the
  store. The limits are named constants. The active schedule count is not
  capped: callers create every schedule and each row is bounded.
- `create` takes a `NewSchedule { spec, jitter, next_run_at }`, so the store
  stays clock-free. `create` on an ended name restarts it in place (same
  id, generation + 1), which is what makes fencing reachable. `Schedule`
  adds `jitter`, `created_at`, `last_outcome` and `stop_reason`. The port
  adds `get(id)`. The generation parameter is named `generation`.
- `Scheduler` adds `new`, `with_missed_tick_policy`, `stop`, `store`, and
  `start_async`/`stop_async`, which run the synchronous store calls on the
  blocking pool. `WorkerHandle::shutdown` bounds the drain.
- `SqliteScheduleStore` uses its own database file and connection, never a
  second connection to another store's file (NFR-BDC-0007 as amended). It
  sets the busy timeout before WAL and checks `PRAGMA user_version`
  (`SCHEMA_VERSION`), refusing an unknown version or a file that already
  holds other tables.

Consequences: a-7 codes against the signatures above. The sprint doc's
Public contract points here.

Amendment (sprint b-6): the contract gains the `enabled` column and flag
(`Schedule::enabled`, `ScheduleStore::set_enabled` and `disable`,
`Scheduler::set_enabled`), `SCHEMA_VERSION` becomes 2 with an in-place upgrade
of a version 1 file, and `CronError` gains `NotFound` and `HookFailed`. See
REQ-CRON-0014, ADR-CRON-0007 and ADR-CRON-0008.

Amendment (PE-RSH-007): `SqliteScheduleStore::list_active` decodes rows one
at a time. A row that fails to decode (`Corrupt`: bad expression, payload
that is not JSON, unknown outcome, bad timestamp) is skipped with a
`tracing::warn` naming its id, name and the error, once per row id per store
instance, and the other schedules are returned and keep running. The row is
left as is, not ended, so it can be repaired. `get(id)` still returns the
`Corrupt` error for that row. Busy, I/O and other non-corrupt failures still
fail the whole call.

## ADR-CRON-0007: Stop decision is continue, disable or delete

**Status:** Approved (Rand's rulings, 2026-10-25); amended by ADR-CRON-0009 (the `Stop` alias is removed)

Context: the stop check could only end a schedule (`Stop(reason)`), and a
schedule could only be ended or left running. A consumer wants a check that
pauses a schedule without losing it, and ANC-006 asks for an enabled flag so a
task can be switched off without rewriting its row. ANC-007 asks for a stop
hook that answers `continue`, `disable` or `delete`.

Decision: `StopDecision` is `Continue`, `Disable(reason)` and `Delete(reason)`.
`Disable` sets `enabled = 0` through the fenced `ScheduleStore::disable`, keeps
the row active with its generation, expression and payload, and stores the
reason as the last outcome, `Refused(reason)`. `Delete` is the old `Stop`: it
ends the schedule with the reason (`ended_at`, `stop_reason`). The row is kept
as the ended record rather than removed, because the id and generation it
holds are what let a restart raise the generation and fence a stale run
(ADR-CRON-0006); a removed row would let a restart start over at generation 1.
A Python stop hook answers `{"action": "continue" | "disable" | "delete",
"reason": "..."}`; `reason` is required for the last two, so a reply that
lost its reason is refused, not acted on. A stop check that cannot answer
(panic, timeout, and for Python a failed start, non-zero exit or malformed
reply) is no decision: the run is skipped and the schedule left active and
enabled, with `Failed` or `TimedOut` recorded.

`StopDecision::Stop(reason)` was kept as an alias of `Delete(reason)` while its
one caller outside this crate, `bd-cache-sync`'s stop rule, existed. That rule
and the alias were removed together by sprint b-8 (the rule was never b-7's to
remove); keeping the alias let the workspace build until then.

*Amended by ADR-CRON-0009:* the last caller moved to sprint b-8, which removes
the alias together with it; sc-cron is an unpublished prototype, so the removal
needs no deprecation period.

Consequences: a disabled schedule is not asked its stop check again until it is
enabled. A job that wants a time limit still checks it in the payload
(ADR-CRON-0001) and answers `Delete`.

## ADR-CRON-0008: Python hooks run as supervised child processes

**Status:** Approved (Rand's rulings, 2026-10-25); amended by ADR-CRON-0009 (the target is resolved per row; the supervisor is exported with an environment policy; `-I` does not clear the environment)

Context: sc-cron must stay general (ANC-005, REQ-CRON-0011), yet a schedule
should be able to run a Python module instead of a Rust `Job`, and b-7 needs
one runner for the consumer's Python sync method and the post-sync hook with
every call killed at its timeout (NFR-BDC-0004). `forbid(unsafe_code)` is set
for the crate, and the kill must reach processes the hook starts.

Decision:

- `HookTarget` is `Rust(Arc<dyn Job>)` or `Python(PythonHook)`, where
  `PythonHook` holds the interpreter and the module. `spawn_worker_for` takes a
  target; `spawn_worker(job)` is `HookTarget::Rust(job)`. The target is held by
  the worker, not stored in the row: a Rust closure cannot be stored, and the
  row stays the opaque spec of ADR-CRON-0001. A caller that wants a row per
  target keeps the choice in its payload.
- A Python target runs `<interpreter> -I -m <module>` (`-I` isolates it from the
  caller's environment, user site and the working directory) from a new
  temporary directory per call, with one JSON object on stdin
  (`protocol`, `event`, `schedule`, `payload`, `deadline`) and the events
  `cron.stop` and `cron.tick`. No name in the protocol is beads-specific. The
  interpreter is an absolute path or a bare command name and the module a
  dotted identifier path, validated once; a relative path with directories
  would be resolved against the temporary directory.
- Every hook is killed at `kill_budget(timeout, deadline, now)`, the row's timeout
  capped by the time left before the run's deadline, on the clock's monotonic
  timeline; the deadline on stdin is the same instant as a UTC time. The wait
  uses the tokio timer. The same kill happens when the run is cancelled, since
  the supervisor kills on drop. A deadline already passed starts nothing.
- The kill takes the whole tree: the child is the leader of a Unix process
  group (killed with `SIGKILL` to the group) or inside a Windows job object
  (terminated, and killed when the job handle closes). `process-wrap` provides
  both with the platform calls inside it, which keeps the crate free of
  `unsafe`; the alternative, calling `libc` and `windows-sys` directly, would
  need `forbid(unsafe_code)` relaxed.
- stdout and stderr are each read to the end and kept up to
  `MAX_HOOK_OUTPUT_BYTES`; stdin is written while they are read, so a hook that
  ignores its input or floods its output cannot stall the supervisor.
- A `cron.tick` hook succeeds by exit 0, otherwise `Failed`; a kill is
  `TimedOut`.

Consequences: a hook should write its answer to stdout and its diagnostics to
stderr. A grandchild that leaves the group or job on purpose (a daemon calling
`setsid`) escapes the kill; if it also keeps the hook's stdout open, the run
lasts until its timeout. The tests use a stub interpreter (a script) on
Unix; the Windows job-object path is checked by compiling it for
`x86_64-pc-windows-msvc`.

## ADR-CRON-0009: The hook target is chosen per schedule row

**Status:** Approved (Rand, 2026-10-26); implemented by sprints b-7 (the store methods) and b-8
(the rest). Amends ADR-CRON-0006 (two store methods), ADR-CRON-0007 (the `Stop` alias is removed)
and ADR-CRON-0008 (the target is resolved per row; the supervisor is exported).

Context: a review of sc-cron's phase-B changes for generality found the scheduler core general,
but one hook target held per worker, so one table could not mix a Rust job and a Python module;
no way to flip several rows' `enabled` flags together, so a caller keeping "at most one of these
enabled" had to do it in steps; a child-process supervisor that a caller running its own child
would have to copy; caller requirement ids and caller purpose in its docs and rustdoc; and a
`Stop` alias kept for one caller. Rand ruled (2026-10-26) that sc-cron stays a general-purpose
cron assembly, that a target is Rust or Python, that general features (such as a multi-row
enable, or exporting the supervisor) are welcome and caller names, paths, types or protocols are
not, and that maturin / PyO3 bindings for sc-cron come when it moves to sc-runtime.

Decision:
- **Resolver.** `pub type TargetResolver = Arc<dyn Fn(&Schedule) -> Result<HookTarget, CronError>
  + Send + Sync>`, an object-safe, synchronous, open extension point: any caller closure maps a
  row to `HookTarget::Rust(Arc<dyn Job>)` or `HookTarget::Python(PythonHook)`.
  `Scheduler::spawn_worker_with(resolver)` spawns a worker that calls it once per launch, before
  the stop check, so a resolver may re-check anything per run. An `Err` is recorded as
  `RunOutcome::Failed(message)` with the schedule left active and enabled, and logged
  (`resolve_failed`). `spawn_worker_for(target)` and `spawn_worker(job)` stay, as resolvers that
  return one target for every row; they are not deprecated.
- **Several rows at once.** `ScheduleStore::set_enabled_many(&[(ScheduleName, bool)]) ->
  Result<bool, CronError>` sets every named active row's flag in one transaction and changes
  nothing (`Ok(false)`) if any name has no active row; `Scheduler::set_enabled_many` (and its
  async form) wraps it.
- **A row written with its flag, and other flags, at once.** `ScheduleStore::replace_and_set_enabled(
  &NewSchedule, enabled: bool, created_at: Timestamp, flags: &[(ScheduleName, bool)]) ->
  Result<Option<Schedule>, CronError>` writes the named schedule with the given `enabled` flag
  and sets each listed other row's flag, in one transaction. The written row: a new name gets a
  new id at `Generation::FIRST`; an ended name is restarted in place, as `create` does; an
  active name is replaced in place, with the same id, generation + 1 (so a run in flight of the
  old row is fenced, REQ-CRON-0007), every field from the argument and its run and end state
  cleared. It never passes through an enabled state it was not given. A listed name with no
  active row changes nothing (`Ok(None)`); a list that names the written row is
  `CronError::InvalidSpec`; the payload limit is `create`'s. `Scheduler::replace_and_set_enabled`
  (and its async form) fills the jitter, the next run and `created_at` from its injected sources,
  as `start` does, and notifies the worker as `set_enabled` does. This lets a caller keep "at
  most one of these rows enabled" across a create or an update, which `create` (always enabled,
  `AlreadyActive` for an active name) and `set_enabled_many` alone cannot.
- **Both are required trait methods, with no default body:** a default made of separate calls
  would not be one transaction and would hide a store that breaks the guarantee. Every
  implementation provides them: `SqliteScheduleStore` in one `BEGIN IMMEDIATE`, `bd-cache-store`'s
  `CacheScheduleStore` the same way (ADR-BDC-0014), and the two `RecordingStore` test doubles
  (`tests/worker.rs`, `tests/common/mod.rs`) by delegating to the store they wrap. These four are
  every implementation in the workspace (sprint b-7).
- **Exported supervisor.** `sc_cron::process` is public: `ChildSpec { program, args, cwd, input,
  env }`, `ChildEnv` (`Inherit`, the default, or `Only { keep, set }`: the environment cleared
  except the named variables, plus the given ones; `keep` holds exact names, so a caller that
  keeps a family such as `LC_*` lists the matching names of its own environment), `TempCwd` (a fresh private directory, removed
  on drop), and `supervise(&ChildSpec, cap, expiry) -> io::Result<Captured>` with the process-group
  / job-object kill at expiry and on drop and the per-pipe cap it has today. `PythonHook` gains
  `with_env(ChildEnv)`, and `HookOutput` gains `stop_decision()` and `run_outcome()`, which apply
  the protocol's rules to an output, so a caller that runs a `PythonHook` inside its own `Job`
  keeps sc-cron's protocol without copying it. Nothing here names a caller.
- **`StopDecision::Stop` is removed;** `Delete` replaces it. The worker's and the hook runner's
  matches on `StopDecision` lose the `Stop` arm. `StopDecision` is not `#[non_exhaustive]`
  (`types.rs`), so removing `Stop` breaks only an exhaustive match outside sc-cron; the
  workspace has one use, `bd-cache-sync`'s stop rule (`job.rs`), which sprint b-8 removes with
  the alias. sc-cron is an unpublished prototype, so the removal needs no deprecation period,
  and no attribute is added.
- sc-cron's docs and rustdoc cite only sc-cron requirements, and its test fixtures use neutral
  names. A child inherits the caller's environment unless the caller sets `ChildEnv::Only`; `-I`
  only makes Python ignore the `PYTHON*` variables, the user site and the working directory on
  `sys.path`.
- No caller-specific protocol, option or name is added.

Consequences: a caller with its own protocol for a child process runs it through
`sc_cron::process` and adds no supervision code or dependency of its own (beads-cache does, for
its post-sync hook, ADR-SYNC-0008); a caller that needs more around a Python row (a lease, a
trust check) wraps it in its own `Job` and the resolver.

## ADR-CORE-0001: Threading model

**Status:** Approved (lead ruling, 2026-10-23)

Context: the store holds one SQLite connection per process (NFR-BDC-0007),
and backend calls block for up to their deadline.

Decision: a `Cache` is `Send` and deliberately `!Sync` (a
`PhantomData<Cell<()>>` marker, whatever the store type is). Every verb runs
synchronously on the caller's thread; reads take `&self`, verbs that store
or call bd take `&mut self`. There is no internal locking and no background
thread: a scheduler (`bd-cache-sync` on sc-cron, or a consumer's
own scheduler through the bindings) owns one `Cache` per cache file and
calls `drain` and `sync` from its tick. Async front ends move the `Cache`
into a blocking task, or keep it behind their own mutex. Across processes,
the drain lock (`DrainLock`) admits one drainer, and the store's
transactions keep each write atomic. The backend and the cache share one
`Arc<dyn Clock>`, so every deadline is measured on one clock.

Consequences: no `Cache` is ever shared between threads by reference; a
second process (a hook) opens its own `Cache` on the same file and contends
only for the drain lock. *Sprint b-7 note (B7Q1-025):* since ADR-BDC-0014
`SqliteStore` is `Send + Sync` (its connection is behind the mutex it shares
with `CacheScheduleStore`); the guarantee is the `Cache`'s marker alone, pinned
by `crates/bd-cache/tests/threading.rs` (`Cache` is `Send` and not `Sync` over
a `Sync` store) and `crates/bd-cache-store/tests/phase_b_store.rs` (the store
and its view are `Send + Sync`).

## REQ-SYNC-0004: The tick budget

**Status:** Approved (lead ruling, bc-lead, 2026-10-24); amended by REQ-BDC-0703's phase-B amendment

A tick drains with `DrainBudget { start_gate: T - 5 s, hard: T - 2 s }`, then
syncs each active phase with deadline `T`. A phase whose sync has not started
by `T - 2 s` is deferred, which is not a refusal. With every `bd` call timing
out, no tick takes longer than 25 s.

**Status:** Approved (lead ruling, bc-lead, 2026-10-24); amended by ADR-SYNC-0008 (the run takes the lease and the budget, not a sender or the `[tick]` keys, and replies without `refused` / `pass-through`)

## ADR-SYNC-0002: The cache lives in an `Arc<Mutex<_>>` and runs under `spawn_blocking`

**Status:** Approved (lead ruling, bc-lead, 2026-10-24)

Context: ADR-CORE-0001: a `Cache` is `Send`, `!Sync`, its verbs block, and
`sc-cron` times a run out by dropping its future, which never stops a
blocking thread.

Decision: `SyncJob` holds `Mutex<Cache>` in an `Arc`. Each run and each stop
check is a `spawn_blocking` task that `try_lock`s the mutex: if it is held
(by the previous tick's task that outlived its timeout, or by the host's own
`with_cache` call) the run is `Refused("busy ...")` and the stop check
answers `Continue`. A `Poisoned` mutex is recovered with `into_inner` and its
poison cleared, and a shared flag remembers that nobody has reported it;
whichever of the stop check and the run recovers it, the next tick's reply
carries `poisoned` once, also when that tick fails (the failed outcome names
it). The run's deadline `Instant` becomes `T` through `Deadline::at`, so every
`bd` call inside the tick is capped at the time left (NFR-BDC-0004), which
bounds how long a left-over task can hold the mutex. The stop check has its
own small bound (`STOP_CHECK_BUDGET`, 3 s) because it runs before every run
and shares the schedule's budget with it. A cooperative `StopFlag` ends a
running tick between phases and before each message and, given to the
consumer's message sender, kills its child; the shutdown order is: set the flag, await the
worker's shutdown, drop the job. `SyncJob::new` validates the `[tick]` table,
so a job that could never run is not built.

Consequences: a tick never waits for a mutex, so ticks cannot queue up
behind a stuck task; the host's own reads and writes use `with_cache` (which
waits, so not from async code) or `try_with_cache` (which does not).

Amendment (phase-end fix, S55, PE-RBP-F007): a poisoned mutex is no longer
trusted. A panic may leave the `Cache` between two steps of a verb, so
whoever meets the poison (the stop check, a run, or a host call) drops the
cache, clears the poison and sets the unreported flag; the mutex holds
`Option<Cache>`. The next tick, or host call, rebuilds it with the recompose
function given to `SyncJob::with_recompose` (the host passes `compose` over
the same inputs, so the same lock set and `$BEADS_DIR`) and its reply carries
`poisoned` once, as before. The stop check never recomposes: it answers
`Continue`. A job built with `new` / `with_stop` has no recompose function:
it reports `TickRun::Lost` (`sync_cache_lost`) and `with_cache` /
`try_with_cache` return `CacheLost`; a recompose that fails is
`TickRun::Lost` with the `ComposeError` as its cause, and is tried again by the
next tick. Evidence: `a_poisoned_mutex_drops_the_cache_and_the_next_tick_recomposes`,
`a_tick_that_panics_in_the_backend_is_not_reused_and_the_next_run_recomposes`
(a panicking backend under `spawn_blocking`; the panicked cache is shown
dropped by the backend's handle count),
`a_poison_met_by_the_stop_check_is_still_reported_by_the_next_tick`,
`a_job_without_a_recompose_function_reports_the_cache_lost_after_a_panic`,
`a_recompose_that_fails_is_tried_again_by_the_next_tick`
(`tests/job_threading.rs`).

Amendment (phase-end fix, PE-RSH-004): the shutdown order waits for the tick
in flight. `sc-cron` drops a timed-out run's future but never its
`spawn_blocking` thread, so after `WorkerHandle::shutdown` a tick may still
hold the cache. The order is now: (1) set the stop flag; (2) await
`WorkerHandle::shutdown`; (3) `SyncJob::join_idle(deadline)` from a blocking
thread, which takes the cache mutex with a timeout (a `try_lock` poll every
5 ms up to the deadline) and returns `true` once no tick holds it, `false` at
the deadline; (4) drop the job. `job.rs` documents the same steps. Evidence:
`join_idle_waits_for_the_tick_in_flight_up_to_its_deadline`
(`tests/job_threading.rs`: a tick held in its `bd list` keeps `join_idle`
waiting until its deadline, and a released tick ends it early).

Note (fix-a-7-3, lead ruling S20, QA3-005): the drain keeps its own budget and
does not look at the stop flag; a stop that arrives while it runs is seen when
it returns. The worst-case shutdown delay while a drain runs is therefore the
drain's hard deadline, `T - 2 s`: the start gate (no new entry starts after
`T - 5 s`) plus one `bd` call (the entry in flight is capped at `T - 2 s`).
`control.rs` implements this and `tests/tick_budget.rs` tests it.

Note (fix-a-7-4, QA4-006, extends the S20 note; **Status:** Approved (lead ruling S24, bc-lead, 2026-10-24)): the flag is also checked after the cached root reads and before
the one `bd list --id` of the uncached roots (ADR-SYNC-0005). A stop that is
set by then does not start that call; the tick replies `stopped` with no sync
and no message, so a stop that arrives after the drain waits at most for the
store reads of the roots. A stop that arrives while that call runs is seen
when it returns, within the miss-fill timeout. `active.rs` implements this and
`a_set_stop_flag_skips_the_root_refresh` tests it.

`bd-cache-model`'s `sender.rs` in sprint b-8).

Context: ADR-BDC-0010 removes every consumer concern from the sync; ADR-BDC-0011 places the
sync on sc-cron rows in the cache file, with a consumer's Python sync replacing the built-in
one when needed and a post-sync hook. Rand ruled (2026-10-26) that the switch is two cron rows
with a CLI convenience that runs the Python row at once and rolls back on failure; that sc-cron
stays a general-purpose cron assembly with a Rust or Python target per row; and that `cron run`
stops new triggers on a signal, waits for runs in flight up to a timeout, kills hanging process
trees and releases the lease.

Decision:

- **Rows and payloads.** Two sc-cron rows, named `bd-cache.sync.builtin` and
  `bd-cache.sync.python`, at most one of each per cache file; other sc-cron rows are allowed. The
  payload is `SyncPayload`, one serde enum tagged by `target`, decoded by one constructor:
  `Builtin { budget: TickBudget, hook: Option<PostSyncHook> }` (`PostSyncHook` is the
  interpreter, the `module:function` and the `--env` names) and `Python { interpreter, module,
  cache_path, beads_dir, env, timeout_ms }`. `TickBudget` (`budget_ms` 1000–600000,
  `hook_reserve_ms` 0 to `budget_ms − 1000`, at least 1000 with a hook) and `FailingSince` (an
  opaque token) are `bd-cache-model` types; `SyncPayload` and `TrustedInterpreter` are
  `bd-cache-sync`'s. `TrustedInterpreter::new` requires an absolute path to a regular
  executable file and then calls `sc_cron::PythonHook::new`, so the module rule has one parser.
- **Resolver.** bd-cache-sync passes sc-cron a resolver (ADR-CRON-0009) that sc-cron calls before
  every launch. It decodes the payload, runs the trust check, and returns
  `HookTarget::Rust(BuiltinSyncJob)` or `HookTarget::Rust(PythonSyncJob)`. A payload it cannot
  decode, a Python sync payload on any row other than `bd-cache.sync.python`, or a failed trust
  check is an error: sc-cron records `RunOutcome::Failed` and leaves the row active, and
  `schedule show` flags the row.
- **Trust.** `TrustedCacheFile` is a proof value only the trust check builds: the cache file is
  owned by the current user and is neither group- nor world-writable (Unix; the Windows ACL check
  is a documented gap). The hook runner and `PythonSyncJob` take it by value, so no code of a row
  or hook runs without a check made for that launch; `cron run`, `cron run --once`,
  `sync use-python` and `tick` all go through it. The check runs, and builds a fresh proof, per
  launch, so the `cron.stop` and `cron.tick` launches of one run each get their own; the proof
  is neither `Clone` nor `Copy`.
- **Mode switch.** The sync mode is `Builtin` (the built-in row enabled), `Python` (the Python row
  enabled) or `None` (neither). Every write of a row or of the rows' flags is one sc-cron store
  call in one `BEGIN IMMEDIATE` transaction (`replace_and_set_enabled` or `set_enabled_many`,
  REQ-CRON-0017), so no connection ever sees both rows enabled, not even while a row is
  created:
  - `schedule set` writes the built-in row with `replace_and_set_enabled`. An existing row keeps
    its `enabled` flag, so `schedule set` after `schedule disable` leaves it disabled; a new row
    is enabled unless the Python row is enabled, and is written disabled while it is. A row
    written enabled also disables the Python row, if one exists, in the same call, so of two
    racing writers the last to commit decides the mode and the invariant holds. An active row is
    replaced in place (generation + 1), so a run of the old row still in flight is fenced and
    records nothing (REQ-CRON-0007); the update never re-enables a disabled row.
  - `sync use-python`: check the inputs (`TrustedInterpreter`, `-I -c 'import bd_cache_rs'`
    within 5 s, the module, the timeout), take the lease, read both rows, then one
    `replace_and_set_enabled` writes the Python row enabled (a new row, or the one Python row
    replaced in place with the new interpreter, module, expression, timeout and `--env` names)
    and disables the built-in row if there is one; then run the row at once under that lease
    (below). On any failure, one transaction restores the state held before the command: the
    Python row's previous contents and flag (or, when there was none, the new row disabled) and
    the built-in row's previous flag. So a failure from mode `Builtin` returns to `Builtin`, a
    failed re-run from mode `Python` returns to `Python` with the previous script, and a failure
    with no built-in row leaves both rows disabled, mode `None`. The command then fails with
    `TICK_RUN_FAILED`; a failed restore is reported (`details.restored: false`) with `sync
    use-builtin` as the recovery. A re-run of `use-python` replaces the one Python row and never
    adds a second; a Python sync payload on any other row is refused by the resolver.
  - `sync use-builtin` takes no lease and calls `set_enabled_many` to enable the built-in row and
    disable the Python row (if one exists); with no built-in row it is `SCHEDULE_INVALID`
    (`details.reason: "no_builtin_row"`), naming `bdc cache schedule set`. Otherwise it always
    works, which makes it the recovery.
  - `schedule enable` of the built-in row while mode is `Python` is `SCHEDULE_INVALID`.
  - A crash after the mode commit and before the run ends leaves the Python row enabled and the
    built-in row disabled, which keeps the invariant; `schedule show` flags a Python row that has
    never run. A signal to `use-python` during the run kills the script's tree, restores the
    state held before the command, then exits `128 + signal`.
- **One sync at a time.** `TickLease` is an RAII guard over the `tick_lease` row: taken under
  `BEGIN IMMEDIATE` (refused while a live lease is held, taken over once expired), with expiry
  at the run's deadline plus 10 s, released when the guard drops (a failed release is logged and
  left to expiry; a `kill -9` is covered only by expiry). Every run takes it first, the built-in
  row's, the Python row's (`PythonSyncJob::run`), an on-demand `tick` and the immediate run of
  `use-python`, and the run functions take `&TickLease`, so no sync work runs without it.
  `sync use-python` passes its `&TickLease` to `PythonSyncJob`'s inner run function, so its
  immediate run never takes the lease again; a scheduled run that finds a live lease returns
  `RunOutcome::Refused("in_flight")`. On a run aborted mid-await, the guard's drop hands the
  release to `spawn_blocking` when a tokio runtime is current; one that does not finish is left
  to expiry.
- **The built-in run.** `Budget` is made from the run's start and its `TickBudget` and hands out
  two deadlines only: the sync deadline (start + `budget_ms` − `hook_reserve_ms`), which the drain
  and the scope syncs get, and the hook deadline (start + `budget_ms`). Steps: lease; drain;
  sync each configured scope by its filter (ADR-BDC-0013), rows stored through the strict decoder,
  all or nothing per scope, the newer-row guard kept, an unreachable bd recorded as an `outage`
  result; the post-sync hook, if named and not backed off; the reply. No write transaction and no
  drain lock is held while the hook runs. The row's sc-cron timeout is `budget_ms + 10000`. While
  mode is `Python`, an on-demand `tick` is `PRECONDITION`.
- **Post-sync hook.** Run through sc-cron's exported supervisor (REQ-CRON-0018) as `<absolute
  interpreter> -I -m bd_cache_rs.run post_sync <module:function>`, from a private temp cwd, with
  the environment cleared except `PATH`, `HOME`, `LANG`, `LC_*` (expanded by bd-cache-sync to
  the `LC_` names in its own environment at each launch), `BEADS_DIR`, `BD_CACHE_PATH` and the
  row's `--env` names, stdout and stderr each capped at 1 MiB, the request written while the
  output is read, and the tree killed at the hook deadline. Request (`bd-cache.run.v1`):

  ```json
  {"protocol": "bd-cache.run.v1", "kind": "post_sync", "run_id": "...", "now": "...",
   "deadline": "...", "cache_path": "...",
   "drain": {"applied": 0, "escalated": 0, "error": null},
   "scopes": [{"scope": "...", "result": "ok|failed|outage|skipped",
               "error": {"code": "...", "message": "...", "outage": true},
               "failing_since": "<opaque token or null>", "notified": false}],
   "escalated": [{"seq": 1, "bead": "...", "op": "...", "actor": "...", "attempts": 3,
                  "error": {"code": "...", "message": "..."}, "created_at": "...",
                  "first_offered_at": "..."}],
   "escalated_truncated": false, "escalated_remaining": 0,
   "pending": {"count": 0, "oldest_age_s": null}}
  ```

  `escalated` holds the escalated, unnotified entries, oldest first, at most 500, and the whole
  request at most 4 MiB (entries are dropped from the end until it fits, and counted in
  `escalated_remaining`); `first_offered_at` is set the first time an entry is offered and never
  changes. The result is optional JSON, kept truncated to 8 KiB; stderr is kept truncated to
  8 KiB. Request bodies are never logged. A failure (spawn failure, timeout, non-zero exit,
  oversize or malformed output, wrong protocol, untrusted cache file) is `TICK_RUN_FAILED` in the
  run's `hook` step, and the run itself marks nothing. Consecutive failures are counted in
  `hook_state` and backed off by periods of the row, one period being the gap between the row's
  next two scheduled times at evaluation (REQ-BDC-0727, QA97R2-016); the hook must be idempotent. The hook reads its
  own configuration; any variable it needs is named with `--env`, and the error's
  `suggested_action` says so.
- **`bd_cache_rs.run`.** Opens its own `Cache` on `BD_CACHE_PATH`, imports the function, calls
  `func(cache, request)` and prints `{"protocol": "bd-cache.run.v1", "ok": true, "result": …}`,
  or `{"ok": false, "error": {"type", "message"}}` with the message truncated to 4 KiB and no
  request data, then exits 0, or 1 on error. `flush`, `drain`, `tick` and `schedule_*` raise
  `PRECONDITION` inside a run.
- **The Python sync row.** `PythonSyncJob` runs the consumer's module with sc-cron's Python hook
  protocol (`sc-cron.hook.v1`) through `PythonHook`, configured with the environment allowlist
  above: `cron.stop` (its `should_stop`), then, on `continue`, `cron.tick` (its `run`, under the
  lease), each from a fresh temp cwd with one JSON object on stdin, `{"protocol":
  "sc-cron.hook.v1", "event", "schedule", "payload", "deadline"}`, where `payload` is the row's
  payload plus the run's `run_id`. The immediate run of `use-python` is the same two calls. The
  stop check runs before the lease is taken, so two workers may each launch `cron.stop`; that
  duplicate is accepted (a `cron.stop` answer has no side effects), and only the lease holder
  launches `cron.tick`. The
  script answers `cron.stop` with `{"action": "continue"}`; `bd_cache_rs.sync.main(func)` is the
  harness that does so and, on `cron.tick`, opens `Cache(payload["cache_path"],
  beads_dir=payload["beads_dir"])` *(superseded by the implementation notes below: it opens
  `Cache(payload["repo_root"], cache_path=payload["cache_path"])`)* and calls `func(cache, payload)`, exiting 0 on return and 1
  with the exception's type and message on stderr. sc-cron keeps up to 64 KiB of each pipe;
  replies and `schedule show` keep stderr truncated to 8 KiB with the values of the row's `--env`
  variables replaced by `<redacted:NAME>`. The run is judged by its exit status; its timeout is
  the row's `timeout_ms` (default 60000, 1000–600000), the immediate run's too.
- **Run id.** Every run gets a `run_id` (`<unix-ms>-<pid>-<counter>`), stored in the lease row,
  passed in the Python payload and the hook request, logged with every step and every
  `ingest_scope` outcome, and returned in the replies and `schedule show`.
- **`cron run` and shutdown.** `cron run` runs sc-cron's `Scheduler` worker on a multi-thread
  tokio runtime (`bd-cache-cli` gains `tokio` with `rt-multi-thread` and `signal`, from the
  workspace entry) with `MissedTickPolicy::Skip`. `bd-cache-cli` depends on `sc-cron` directly, a
  new Boundaries edge `bd-cache-cli` → `sc-cron` that sprint b-8 adds with the code: the CLI
  constructs the `Scheduler` over `CacheScheduleStore` with bd-cache-sync's resolver, and
  bd-cache-sync does not re-export sc-cron's API. *(Superseded by the QA-1 amendment below
  ("One surface"): `bd-cache-cli` no longer depends on `sc-cron`; `cron run` is
  `Schedules::cron_run` in bd-cache-sync.)* `SIGINT` and `SIGTERM` (Ctrl-C and Ctrl-Break on
  Windows, through `tokio::signal::windows`) set the `StopFlag` and `sc_bd_cli::shutdown::request`
  *(superseded by the QA-1 amendment below ("Shutdown"): on a signal only the stop flag is set;
  the bd calls are stopped only when the shutdown timeout expires)*,
  then call `WorkerHandle::shutdown(now + --shutdown-timeout-ms)`: no run is launched, runs in
  flight are awaited to that deadline, and those still going are aborted, which drops their
  supervisors and kills the hook's and the Python row's process trees (process group or job
  object); the built-in run's blocking part sees the `StopFlag`, its bd calls stop on the request,
  and it returns and drops its `TickLease`. Exit codes are REQ-BDC-0730's. `SIGHUP` is handled as
  `SIGTERM` (exit 129). A second signal during the wait ends it at once, as the timeout's expiry does (`Schedules::cron_run_hurried`; *amended at the phase-end review, REQ-BDC-0730 as amended: it was ignored before*). `cron run --once` runs
  what is due, waits for each run it started to its own deadline, and exits 0, or 3 with
  `TICK_RUN_FAILED` listing each failed row.
- **Logging.** `cron run` installs its stderr subscriber as the process default, so sc-cron's
  events (`launched`, `timed_out`, `recorded`, `fenced`, `reload_failed`) from runtime threads
  and the signal thread are kept, at the `-v` / `-q` levels; each run logs one structured event
  per step (lease, drain, each scope, hook, reply) with the row, the `run_id` and the outcome.
- **`schedule set` and `schedule show`.** `schedule set` validates the expression, the budget
  pair and, with `--post-sync`, the interpreter (`TrustedInterpreter`, then `-I -c 'import
  bd_cache_rs'` within 5 s) and the `module:function`, all before writing; each refusal is
  `SCHEDULE_INVALID` naming the field. The import check runs through sc-cron's exported
  supervisor with the row's environment allowlist and is killed with its tree at 5 s. The row is
  then written as the mode switch says, its `enabled` flag kept. `schedule show` reports what
  REQ-BDC-0731 lists.
- **Dependencies (amends ADR-SYNC-0006).** After b-8: `bd-cache`, `bd-cache-model`,
  `bd-cache-store`, `sc-bd-cli`, `sc-cron`, `sc-beads`; `tokio`, `async-trait`, `serde`,
  `serde_json`, `tracing`; and, on Unix only, `rustix` with its `process` module (QA97R2-014).
  `TrustedCacheFile` compares the cache file's owner with the process's effective uid, and
  `rustix::process::geteuid` is a safe call: this crate keeps no `unsafe` and adds no crate to
  `Cargo.lock` (rustix is already there through `tempfile`; only its `process` feature is turned
  on), named directly in this crate's manifest, so the root `Cargo.toml` is not edited
  *(superseded by sprint b-8's QA-1 fix round, B8Q1-036: `rustix` and `process-wrap` are
  `[workspace.dependencies]` entries of the root `Cargo.toml`, each with its reason there, and
  this crate takes `rustix` with `workspace = true`)*. `toml`
  and `libc`, which served the phase files, are removed with them. No other dependency is added:
  the child-process supervision and the temp cwd are sc-cron's exported API, so there is no
  `process-wrap`, `windows-sys` or runtime `tempfile` here; the root `libc` entry stays until a
  later root-manifest change.

Rejected alternatives: an in-process Python call (it would hold the GIL and the store across
user code); code named in `.beads/bd-cache.toml` (it may be checked in); r3's per-scope methods
with a registered `sync` method called inside the tick (superseded by the two-row ruling); a
third hand-rolled child supervisor in this crate (new dependencies, and a third copy beside
sc-cron's and sc-bd-cli's that could diverge); the Python row as a bare `HookTarget::Python` with
a per-row run lock in sc-cron (a schema change to sc-cron's own store, and a lock that would not
exclude the built-in row or the immediate run).

Consequences: the sync reaches the backend only through bd (REQ-BDC-0006); every bd call, hook
and script run is bounded by its deadline (NFR-BDC-0004); the register (REQ-BDC-0720..0732)
states the behaviour, and b-9's contract text follows it.

## REQ-PY-0006: Threading

**Status:** Approved (lead ruling, bc-lead, 2026-10-24)

The handle keeps the `Cache` behind a mutex (ADR-CORE-0001: a `Cache` is
`!Sync`, so a shared owner guards it). Any Python thread may call a verb,
close the handle or drop it; verbs run one at a time, and no cross-thread use
panics. Each verb, `close()`, `__exit__` and `closed` release the GIL or take no
lock: `closed` is an atomic flag, true as soon as `close()` begins; `close()`
waits for the in-flight verb with the GIL released and drops the connection
there. A verb that panics is caught at the panic: the connection is dropped and
the handle closed before the call returns (so `closed` is already true and the
cache file can be opened again), and that call and every later one raise
`ClosedError`; no `PanicException` reaches Python. Other Python
threads continue while a verb waits on `bd` or SQLite.

**Acceptance evidence:** `test_a_python_thread_runs_while_a_verb_waits_on_bd_and_releases_it`,

## ADR-PY-0001: A thin layer over the concrete composition

**Status:** Approved (lead ruling, bc-lead, 2026-10-24)

Context: REQ-BDC-0910 asks for the cache in process from Python. The core is
generic over its store, lock and backend, and the bindings must pick types.

Decision: the handle owns `Cache<SqliteStore, FlockDrainLock, BdCli>` and a
`SystemClock` that `Cache` and `BdCli` share (the core's rule that deadlines
are measured on one clock). `Cache.__init__` follows the repository
configuration rules of `docs/architecture.md`: it loads `.beads/bd-cache.toml`
with `bd_cache_store::load_repo_config`, applies the keyword overrides,
opens the store (which locates the file from `.beads/metadata.json`; no `bd`
starts), and runs `bd` as `bd_binary` in `project_dir` (default: the
repository root). Each verb parses its arguments into the validated newtypes
(`BeadId`, `Actor`, `IdemKey`, `ScopeId`) and calls the `Cache` method of the
same name. The binding adds no rule: a defect in a rule is fixed in
`bd-cache`, and the pytest suite checks that the verbs reach it with the
right arguments (the argv `bd` saw) and return what it returned.

Dependencies (lead ruling R2, R3): the crate takes `bd-cache`, `bd-cache-store`,
`bd-cache-model`, `sc-bd-cli` and `sc-beads` through `[workspace.dependencies]`
(`bd-cache-store` and `sc-bd-cli` were added there for this crate), and the
third-party `pyo3`, `serde`, `serde_json` and `dunce` (the last for canonical
paths, lead ruling R12). `serde` is used only for the
`Serialize` bound of replies.

One `ProjectLocks` set per process (a `OnceLock` in `compose`) is shared by every
handle, keyed by the canonical project directory (`dunce::canonicalize`: the
std canonical path, without the Windows `\\?\` verbatim prefix where the plain
form is valid; `dunce` is a workspace dependency added for this crate, lead
ruling R12, bc-lead, 2026-10-24; an unresolvable directory is refused): `bd` on embedded Dolt must not run twice at once in a project, and two
handles on one project (different cache files) would otherwise each lock
separately. It is the only static; it is correctness state and the libraries
(`sc-bd-cli`) still take the set as an argument. *(Superseded by the QA-1 amendment of
ADR-PY-0006 below: the in-run flag is a second static, and the `ProjectLocks` set is
`bd-cache-sync`'s, with `dunce` dropped.)* The deadlines of `sync` and
`drain` are minted from the `Arc<dyn Clock>` that the `Cache` and `BdCli` share.

Consequences: a different backend (HTTP, later) needs a new composition and a
new handle type; the Python verbs stay the same. The default cache file is
`.bd-cache/<dolt_database>.bd-cache.sqlite3`; the first consumer keeps its
existing file in its own directory by setting `cache_path`.

## ADR-PY-0002: Replies are builtin objects; one exception class

**Status:** Approved (lead ruling, bc-lead, 2026-10-24); amended by lead rulings S38/S42 (bc-lead, 2026-10-24, fix-a-7-12): the config kind is reserved

Context: the first consumer reads the baseline Python implementation's JSON
dicts today. The `bd-cache-model`
reply types derive `Serialize`.

Decision: a reply is `serde_json::to_value` of the Rust reply, converted
recursively to `dict` / `list` / `str` / `int` / `float` / `bool` / `None`.
No Python class mirrors a reply, so the shapes below are the whole contract
and change only with the wheel's version. The shapes are the Rust ones

`None`. *(Amended below, sprint b-9: the `config` kind is removed.)* An unreadable config
file is an `OSError` of kind `read`.

Consequences: `error.extra` of the baseline Python implementation is
`error.payload`; its
`as_json()` is `error.body`.

## ADR-PY-0003: Threading

**Status:** Approved (lead ruling, bc-lead, 2026-10-24); the one-connection rule is restated for the phase-B methods by ADR-PY-0006

Context: ADR-CORE-0001: a `Cache` is `Send`, `!Sync`, owns one connection,
and every verb is synchronous. A verb can wait on `bd` for up to its deadline.
The first draft made the handle `#[pyclass(unsendable)]`; a handle touched or
dropped on another thread then panicked inside PyO3 (seen on CI: a test thread,
and a Python object freed by whichever thread held the last reference).
That cannot be allowed for an object a scheduler may hand between threads.

Decision (amends the sprint doc's "unsendable" wording, per lead ruling of
2026-10-24 on PR #11): the handle owns `Mutex<Option<Inner>>`, the "behind
their own mutex" option ADR-CORE-0001 names. The handle is `Send + Sync` to
PyO3; any thread may call a verb, `close()` or drop it. Verbs run one at a
time. Every verb takes the lock and runs inside `Python::detach`, so a thread
waiting for the lock or for `bd` holds no GIL. `closed` is an atomic flag set
as `close()` begins; `close()`, `__exit__` and `closed` never hold the GIL
while they wait: `close()` waits for the in-flight verb inside `Python::detach`
and drops the connection there. A verb runs under `catch_unwind` inside the
slot: if it panics, the slot takes and drops the connection (it may be
mid-statement) and sets `closed` before the call returns, so the cache file can
be opened again at once, and the call raises `ClosedError` carrying the panic
message and telling the caller to open a new `Cache`; later calls raise it too.
No `PanicException` reaches Python. (Built with `panic = "abort"` a panic
aborts the process, which is what a panic means.) A lock poisoned outside a
verb (a panic in a `Drop`; defensive, nothing in production does this) is handled
the same way: the value is dropped, the poison is cleared while the guard is
held, and the first call reports it.
Nothing reuses a connection after a panic. Replies are converted after the GIL is taken again. SQLite
allows one connection per process per file (NFR-BDC-0007), so a second open
of the same file in the process is `STORE_IN_USE`; threads that want to run
verbs in parallel open different files.

Consequences: no background thread, no unsafe, no panic path for cross-thread
use. A long verb blocks other threads' verbs on the same handle (not their
Python code).

## ADR-PY-0006: The phase-B methods, the mixed layout and the bd-cache-sync edge

**Status:** Approved (Rand, 2026-10-26); implemented by sprints b-8 (layout, methods, edge) and
b-9 (the test strategy). Amends ADR-PY-0004 (packaging and tests) and ADR-PY-0005 (its "No tick"
and "Boundaries" bullets and its scope sentence); restates ADR-PY-0003's one-connection rule for
the new methods; supersedes REQ-PY-0009 with the vendored call log.

Context: phase B adds `Cache.tick()`, `schedule_*`, `sync_use_python` / `sync_use_builtin`,
`ingest_scope`, `scope_announce` and `scopes_*` (REQ-BDC-0720..0731), and two Python entry points
run as `-m` modules: `bd_cache_rs.run` for the post-sync hook and `bd_cache_rs.sync` for a
consumer's sync script (ADR-SYNC-0008). ADR-PY-0005 says the crate does not depend on
`bd-cache-sync`; the pyproject builds one extension module named `bd_cache_rs`, which cannot also
hold Python submodules; and S84 removes the vendored call log the mapping test reads.

Decision:
- **Edge.** `bd-cache-py` depends on `bd-cache-sync` (a new Boundaries row edge, made by b-8 with
  the code) and on `tokio`, the workspace entry, whose `rt` feature builds the current-thread
  runtime below; b-8 names it in the crate's Crate Layout row. It needs no `sc-cron` edge: the
  schedule and switch calls go through `bd-cache-sync`. `Cache.tick()`, `schedule_*` and `sync_use_*` call `bd-cache-sync`; the store-only
  methods go through `bd-cache-api` like the 0.2 namespaces (ADR-BDC-0015).
- **One connection.** Every new method runs on the handle's own `Cache` and connection, under its
  mutex and inside `Python::detach` (ADR-PY-0003); `schedule_*` and `sync_use_*` use the handle's
  `CacheScheduleStore` (ADR-BDC-0014), so the process opens no second connection.
- **Runtime.** `Cache.tick()` and `sync_use_python()` release the GIL (`Python::detach`), then
  build a current-thread tokio runtime on a helper thread the call spawns and joins, and drop it
  before returning: no runtime outlives the call, and a caller on an asyncio event loop thread or
  inside a tokio runtime of its own never has a runtime nested in its context. An asyncio caller
  that does not want to block its loop calls them through `loop.run_in_executor`, as for every
  other verb. Both run the post-sync hook and the Python row as subprocesses (S90); nothing runs
  user code in process. Like the 0.1 `sync` verb, they hold the handle's mutex (and its one
  connection) for the whole call, so another thread on the same `Cache` waits until the run's
  deadline at most, and the call cannot be interrupted from Python. *(Superseded by the QA-1
amendment below: a `KeyboardInterrupt` during the call stops the run and is raised when it
returns.)*
- **Layout.** maturin's mixed layout: the native module is `bd_cache_rs._native` (`module-name =
  "bd_cache_rs._native"`, `#[pymodule] fn _native`), and `crates/bd-cache-py/python/bd_cache_rs/`
  holds `__init__.py` (re-exporting every 0.1 and 0.2 name from `_native`, with the same
  `__all__`, `__version__` and `CONTRACT_VERSION`), `run.py` (`python -m bd_cache_rs.run`) and

## ADR-CLI-0001: Historical git dependency and unpublished CLI

**Status:** Approved (lead ruling S60, bc-lead, 2026-10-25; phase B closed, 2026-10-25)

Context: the CLI replies in sc-command's `Envelope` (contract §4, ADR-BDC-0009).
sc-command is in randlee/sc-runtime and is not published to crates.io; a crate
with a git dependency cannot be published. The three crates that are published
(`sc-beads`, `sc-bd-cli`, `sc-cron`) have no such dependency, and CI dry-runs
their publication.

Decision:

- sc-command is a git dependency on `https://github.com/randlee/sc-runtime`
  at the stable tag `v0.1.0` (`ae3e10b`), declared once in
  `[workspace.dependencies]`. PR #84 moved the pin there from
  `prerelease/v0.1.0` (`ba971c1`) at the sc-runtime team's request; the crates
  at the two tags are byte-identical. A tag, not a branch, so the build does not move.
  If the tag fails to build on a CI OS, the dependency is pinned by `rev`
  instead and the failure is raised with the sc-runtime team; there is no local
  fork (phase b plan, P-7).
- `bd-cache-cli` is `publish = false`. The CLI ships as binaries (GitHub
  releases and package channels, sprint b-5), not as a crate.
- The crates other than this one (`bd-cache-api` and `bd-cache-py` especially)
  take neither sc-command nor clap, so the published and bound surfaces are
  unaffected. CI checks it.
- `sc-observability-types` (the type of an sc-command error code) is a normal
  crates.io dependency at `1.5`, the version sc-command itself uses.
- `Cargo.lock` is committed, so the git revision is fixed by the lock as well.

The pin was checked first on all three CI OSes (ubuntu, macOS, Windows),
and on a Windows machine over SSH, before the harness was built on it.

Consequences: a release needs network access to GitHub for the dependency.
Moving the pin is a deliberate edit to `Cargo.toml` and `Cargo.lock`. cargo
prints one line, `error: invalid key-value pair, expected key`, for the
`template/` directory of the sc-runtime checkout while it resolves the
dependency; it is cargo's note about a file that is not a manifest, the command
still exits 0, and it is not ours to fix.

## ADR-CLI-0002: `fake-bd` is a feature-gated binary over `FakeBd` with scenario-file state

**Status:** Approved (lead ruling S60, bc-lead, 2026-10-25; phase B closed, 2026-10-25)

Context: contract §8 "Testing" needs a real-process simulator: tests run `bdc`
as a process with `--bd <fake-bd>`, and the NFR-BDC-0002 latency check does too.
sc-bd-cli already has a stateful in-process `FakeBd` over `FakeBackend`
(feature `test-support`), which is the model of bd the rest of the tests use.

Decision:

- `fake-bd` runs that same `FakeBd`; it does not model bd a second time.
- The binary has `required-features = ["fake-bd"]`, and the feature enables
  `sc-bd-cli/test-support` and `sc-beads/testing`. A **self dev-dependency**
  with the feature (`bd-cache-cli = { path = ".", features = ["fake-bd"] }`)
  turns it on for `cargo test`, so the integration tests can use
  `CARGO_BIN_EXE_fake-bd`. A release build (`cargo build --release --bin
  bd-cache --bin bdc`) does not build dev-dependencies and does not build
  `fake-bd`. The boundary check does not count a crate's dev-dependency on
  itself as an edge.
- The state is a file, so that a sequence of processes sees one bd. It is
  loaded on every start and written back (temporary file, then rename) after
  a call that changed a row. Calls are sequential; there is no file lock.
- Faults are fields of the scenario, not flags: they apply to every call of
  the scenario, and a test changes them by rewriting the file.
- The harness code that is not the binary (`scenario`) is part of the library
  behind the feature, so the tests build scenarios with the same type that
  `fake-bd` reads, and a typo in a hand-written scenario is an error
  (`deny_unknown_fields`).

Consequences: `fake-bd` answers only the command forms `FakeBd` serves (the
cache's calls, `version`, `schema`; `--version` as `version`). A bd command it
does not serve is exit 2, as a usage error.

## ADR-CLI-0003: One command table; argv becomes the request the decoder reads

**Status:** Approved (lead ruling S60, bc-lead, 2026-10-25; phase B closed, 2026-10-25); amended by ADR-BDC-0015 (the phase-B verbs)

Context: contract §1 rule 6 puts validation in `bd-cache-api`'s decoder, so
every front end returns the same code for the same input; contract §3 keeps
`USAGE` for the shape of argv.

Decision:

- Each command is one row (`CommandSpec`): path, target, and arguments, each
  naming the `/v0` request member it fills (`patch.status`,
  `edges.0.issue_id`). The clap tree, the request builder and the help come
  from the rows.
- The CLI checks only the shape of argv: clap's required arguments, unknown
  or abbreviated flags (`infer_long_args` off), a member filled twice, and
  `--input` with request flags are `USAGE`. Values go to the decoder as
  given: an integer flag that does not parse is passed as text, so the
  decoder answers `BAD_ARGS` naming the member.
- With `--input`, clap's `required` is lifted and the file is the request.
- The words of argv are pre-scanned for `--help`, `--version` and the `/v0`
  operations the cache does not serve, which are `UNSUPPORTED` before clap
  sees them (`bdc ready count`, `bdc issues create`).
- The request is decoded before the cache is opened.

Consequences: a request member the decoder learns is a flag with one row;
`--help` cannot drift from the grammar.

## ADR-CLI-0005: SIGTERM, SIGINT and SIGHUP stop the bd calls, then bdc exits 128 + signal

**Status:** Approved (phase-end fix RSH-001, bc-lead, 2026-10-25); extended by ADR-SYNC-0008 and REQ-BDC-0730 for the long-running `cron run` (shutdown timeout, process-wide log, Ctrl-C and Ctrl-Break on Windows)

Context: every bounded `bd` child leads its own process group (PE-RSH-001), so
a signal sent to bdc, or a terminal's Ctrl-C to its foreground group, never
reaches the `bd`. With the default action bdc died and left the `bd` and a
`dolt` it started running, holding no lock, so the next call on the project
collided with them (RSH-001).

Decision:

- On Unix `run_process` installs `signal-hook`'s iterator for SIGTERM, SIGINT
  and SIGHUP before any command runs (`commands::signal`, a Unix-only
  dependency, `signal-hook = "0.3"` with only the `iterator` feature). Signals
  are received on a thread of their own; no code of ours runs in signal
  context.
- A signal calls `sc_bd_cli::shutdown::request(signal)`, which every bounded
  call observes: a running child's group is killed and reaped as on a
  timeout, a waiting call starts nothing, and both project locks (the mutex
  and the cross-process file, ADR-BDCLI-0006) are released by the call's
  normal return. It also sets the command's `StopFlag`: `cache tick` runs
  `tick_with` and the consumer's message sender's `with_stop` on it, so the
  tick ends early and the sender's child is killed with its group.
  *Amended by ADR-SYNC-0008 (sprint b-8):* the message sender is removed; the
  `StopFlag` stops `cache tick` and `cron run`, whose shutdown waits for runs in
  flight up to `--shutdown-timeout-ms` (REQ-BDC-0730).
- The command then unwinds normally and writes its envelope (whatever it
  reports: a write already journaled is not hidden); the exit code is
  `128 + signal` (143 for SIGTERM), whatever the envelope says, with one line
  on stderr. A second signal changes nothing: the shutdown is bounded by the
  calls' kill bound (1 s); SIGKILL remains. The exception is `cron run`
  during its shutdown wait, where a second signal ends the wait at once
  (REQ-BDC-0730 as amended at the phase-end review). On Linux the `bd` child also has
  `PR_SET_PDEATHSIG` (SIGKILL), for a bdc killed outright.
- `run` and `run_with` (the in-process entry points) install nothing: the
  host process owns its signals.
- Windows: nothing is installed (no such signals); a console Ctrl-C is out
  of scope. *Amended by ADR-SYNC-0008 and REQ-BDC-0730 (sprint b-8):* `cron run`
  handles Ctrl-C and Ctrl-Break through `tokio::signal::windows`; every other
  command still installs nothing on Windows.

Consequences: the exit codes of contract §3 gain the shell's signal
convention, `128 + N`, for a bdc stopped by a signal (listed there). Test:
`commands::signal::process_tests::sigterm_kills_the_bd_group_and_exits_143`
(a `bdc` whose fake `bd` hangs with a TERM-ignoring grandchild, causal on pid
files), which runs the `bdc` binary `cargo test` builds next to the test.
